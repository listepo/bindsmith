# NativeScript Dynamic API Bridging: Metadata-Driven Runtime Dispatch
## Research Report on Automatic Binding Generation for Cross-Language Native Access

**Date:** 2026-09-08  
**Author:** Research Analysis  
**Scope:** NativeScript iOS/Android metadata generation + dynamic bridge runtime, analogs systems, trade-offs vs. static codegen

---

## Executive Summary

NativeScript exposes 100% of iOS Objective-C/Swift and Android Java/Kotlin APIs to JavaScript without hand-written bindings via:

- **Build-time metadata extraction** (C++ libclang parser for iOS; Java ASM for Android)
- **Binary metadata embedding** in the app bundle (iOS: custom format `metadata-<arch>.bin`; Android: `treeNodeStream.dat` + `treeValueStream.dat` + `treeStringsStream.dat`)
- **Runtime dynamic dispatch** (iOS: `objc_msgSend` via metadata signatures; Android: JNI reflection via metadata method cache)
- **Lazy JS wrapper generation** from metadata at runtime
- **TypeScript definitions** generated by same toolchain (@nativescript/types-ios: 13.2 MB; @nativescript/types-android: 141 MB)
- **Hybrid model for extensibility**: Android's Static Binding Generator (SBG) pre-compiles JS-to-native subclass stubs at build time

This approach achieves API completeness (including Swift via @objc, Kotlin via reflection) at the cost of runtime marshalling overhead (~1.5x native calls for primitives), modest startup cost (metadata decompression), and large type definition packages. Analogous systems: dart_native, PyObjC/BridgeSupport, rubicon-objc, PyJNIus, Chaquopy, Unity AndroidJavaObject, JNA, Dart ffigen/jnigen, Node koffi/ffi-napi.

**Key trade-off**: Metadata-driven (NativeScript style) = 100% coverage, smaller APK (metadata embedded efficiently), slower individual calls; Static codegen (Dart ffigen/jnigen) = curated APIs, tree-shakeable, faster calls, larger build-time footprint.

## 1. NativeScript iOS Runtime & Metadata-Generator

### Overview
NativeScript iOS runtime moved to **V8 engine** (previously JavaScriptCore) with NativeScript 9.0 (Nov 2025). The `ios-metadata-generator` is a C++ tool using Clang's AST to parse all iOS SDK frameworks and user CocoaPods/SwiftPM dependencies.

**Repository:** https://github.com/NativeScript/ios  
**Metadata-Generator Repository:** https://github.com/NativeScript/ios-metadata-generator  
**Latest Version:** NativeScript 9.1 (Aug 2026, V8 14.9)

### How It Works

#### Parser Front-End (C++ libclang)
- Input: iOS SDK headers + user framework headers (via `module.modulemap`)
- Uses libclang AST visitors (`DeclarationConverterVisitor`) to traverse ObjC declarations
- Expands and parses all public APIs
- Filters out implementation details, private APIs

#### Metadata Format
- **Output file:** `metadata-<arch>.bin` (binary, custom format)
- **Embedded in:** `.ipa` (iOS app package)
- Stored as compressed binary with sections for:
  - Class/protocol metadata (names, selectors)
  - Method signatures (ObjC method type encoding)
  - Instance/static methods, properties, ivars
  - Block type information
- Format is pre-generated at Xcode build time and embedded in the app

#### Filtering Mechanism
- `whitelist.mdg` / `blacklist.mdg` files (pattern-based)
- Application-level filtering via `native-api-usage.json` in App_Resources/iOS
- Patterns match framework names and class names (e.g., `UIKit:UIView*` to whitelist only UIView and subclasses)

#### TypeScript Definition Generation
- CLI: `ns typings ios` (part of NativeScript CLI)
- Runs the same metadata-generator with `-output-typescript` flag
- Generates `@nativescript/types-ios` (13.2 MB for iOS SDK definitions)
- Module structure: `UIKit { UIViewController { ... } }` matching ObjC namespace

#### Swift Support
- Only `@objc`-visible Swift APIs are bridged
- Swift-only APIs (no ObjC annotation) are not accessible
- Limitation: Swift generics, some protocol features not fully bridged

#### Runtime Dispatch
- Lazy JS wrapper generation: when JS accesses `UIView.new()`, runtime creates JS constructor from metadata
- Marshalling: `interop` namespace provides `interop.Reference`, `interop.Pointer`, `interop.FunctionReference`
- Native calls: libffi + `objc_msgSend` (or `objc_msgSendSuper`) via metadata method signatures
- Blocks: converted to JS functions; JS callbacks wrapped as ObjC blocks
- Protocols: JS can `implement()` ObjC protocols; conformance checked at runtime

#### Configuration
- Build phase script: `build-step-metadata-generator.py` in Xcode
- CMake build system for metadata-generator tool
- LLVM binaries downloaded via `./download_llvm.sh`

### Performance & Limitations
- **Startup cost:** Metadata decompression (typically <100ms for full SDK)
- **Call overhead:** ~1.5-2x native C for primitives (due to type marshalling)
- **Memory:** JS heap retains native object references; managed via `interop.gc()`
- **Debuggability:** Good; stack traces show JS→ObjC boundary

### Status
**Maintained:** Yes; active development (NativeScript 9.x in 2025-2026)  
**License:** Apache 2.0  
**URL:** https://github.com/NativeScript/ios

## 2. NativeScript Android Runtime & Metadata-Generator

### Overview
Android runtime uses V8 engine. The `android-metadata-generator` is a Java tool that reads compiled bytecode (JAR/AAR) from android.jar + user dependencies to extract all public Java/Kotlin APIs.

**Repository:** https://github.com/NativeScript/android  
**Metadata-Generator:** https://github.com/NativeScript/android-metadata-generator  
**DTS Generator:** https://github.com/NativeScript/android-dts-generator  
**Latest Version:** NativeScript 9.1 (Aug 2026, V8 14.9)

### How It Works

#### Parser Front-End (Java ASM/Bytecode)
- Input: android.jar + all dependency JARs/AARs + app's Java/Kotlin classes
- Uses **Apache Commons BCEL** (or ASM) to iterate compiled class files
- Extracts all public types (classes, interfaces, enums, exceptions)
- Reads generics metadata from class file constant pool (GenericsAwareClassHierarchyParserImpl)
- Recursively resolves superclasses and interfaces

#### Metadata Format (Binary)
Three complementary files in the APK:
- `treeNodeStream.dat` — class hierarchy tree (parent/child relationships)
- `treeValueStream.dat` — numeric IDs and counts
- `treeStringsStream.dat` — class names, method names, field names (string pool)

These are memory-mapped at runtime for fast lookup; design emphasizes minimal memory footprint.

#### Static Binding Generator (SBG)
**Key innovation:** Hybrid static + dynamic approach.

- **Purpose:** When JS calls `extend(NativeClass)`, SBG pre-generates Java mirror classes at build time (compile-time, not runtime)
- **Input:** Parsed JS/TS decorator calls like `@Interfaces(SomeInterface)`
- **Output:** Generated Java classes in `com.tns.gen` package that implement the interface
- **Benefit:** Faster class loading; JNI can bind directly to generated stubs (avoids runtime proxy generation penalty)
- **Generics handling:** GenericsAwareClassHierarchyParserImpl "reifies" generic types at build time (e.g., `ArrayList<String>` → concrete MethodHandle)

#### TypeScript Definition Generation
- CLI: `ns typings android --jar <path>` (generates .d.ts from JAR)
- Tool: `android-dts-generator` (uses ASM to parse bytecode → TypeScript)
- Package: `@nativescript/types-android` (141 MB for framework definitions)
- Generates module hierarchy matching Java package structure
- Known limitation: Kotlin serialization double-dollar-sign names (`$$serializer`) create invalid TypeScript

#### Kotlin Support
- **Native support:** Kotlin bytecode is readable by ASM/BCEL; all Kotlin public APIs are exposed
- **Limitations:**
  - Suspend functions (coroutines) not directly callable from JS (must wrap in async)
  - Kotlin `object` (singleton) and `companion object` access requires special syntax
  - Extension functions appear as static methods on the receiver class
  - Kotlin sealed classes and data classes bridged as-is

#### Metadata Filtering
- **Application-level:** `native-api-usage.json` in App_Resources/Android
- **Format:** Pattern-based whitelist/blacklist
  - Pattern1: Java package name (`java.util`, `android.view.*`)
  - Pattern2 (optional): Class/interface name (`ArrayList`, `*Listener`)
  - Wildcard: `*` (any characters), `?` (single character)
- **Logic:** Whitelisted APIs only; blacklist removes specific entries
- **Debugging:** Metadata logs in `platforms/android/build-tools/mdg-java-out.txt`

#### Runtime Dispatch
- **MethodCache:** Pre-computed JNI method signatures for all public methods
- **JNI layer (JEnv):** Thin wrapper over `GetMethodID` / `CallXMethod` with caching
- **Reflection fallback:** Methods not in SBG can still be called via Java reflection at runtime
- **Callbacks:** JS functions → Java `Runnable`/`Callable` adapters; `CallbackHandlers` manage lifetime

### Performance & Limitations
- **Startup cost:** Metadata decompression + MethodCache initialization (~200-300ms for large SDK)
- **APK size:** Metadata adds ~2-5 MB; type definitions separate (141 MB npm package, not shipped in APK)
- **Call overhead:** ~1-2x native JNI calls for primitives
- **Memory:** Each cached method holds JNI reference; aggressive cache management needed for high-throughput apps

### Status
**Maintained:** Yes; active development  
**License:** Apache 2.0  
**URL:** https://github.com/NativeScript/android

## 3. Plugin Authoring & Zero-Binding Practice

### Native API Access Pattern

Plugin authors typically **do not write any binding code**. Instead:

1. **Call native APIs directly from TypeScript:**
   ```typescript
   import { UIView, UIButton } from '@nativescript/types-ios';
   let btn = UIButton.buttonWithType(UIButtonTypeSystem);
   ```

2. **Use CLI to generate typings:**
   ```bash
   ns typings ios                    # Generates definitions for iOS SDK
   ns typings android --jar path.jar # Generates definitions for Android JAR
   ```

3. **Rely on @nativescript/types packages:**
   - `@nativescript/types` (both platforms)
   - `@nativescript/types-ios` (13.2 MB)
   - `@nativescript/types-android` (141 MB)

### Pain Points Reported

1. **Large type definition packages** — 141 MB for Android makes npm install slow
2. **Startup time** — Metadata decompression delays app launch by 100-300ms on cold start
3. **Swift-only APIs not bridged** — Any Swift API without `@objc` is inaccessible
4. **Kotlin quirks** — suspend functions, object singletons require workarounds
5. **Metadata size in APK** — ~2-5 MB embedded; difficult to tree-shake unused APIs
6. **Marshalling generics** — Java `List<String>` appears as raw `List` in JS; runtime casts needed
7. **Missing JS interop for enums** — Kotlin enums and Java enums sometimes lose semantic mapping
8. **`interop` C API rough edges** — Memory management of `interop.Pointer` requires manual `interop.gc()` calls; no automatic cleanup

### Documentation
- **Native API Access Guide:** https://docs.nativescript.org/guide/native-api-access
- **iOS Marshalling:** https://docs.nativescript.org/guide/ios-marshalling
- **Android Marshalling:** https://docs.nativescript.org/guide/android-marshalling

### Status
**Maintained:** Yes; part of core NativeScript ecosystem  
**License:** Apache 2.0

## 4. Other Dynamic Bridge Analogs

### 4.1 dart_native (Alibaba, Dart)
**URL:** https://github.com/dart-native/dart_native

**What it is:** Dynamic ObjC/Java bridging for Dart via C++ bridge layer + code generation.

**How it works:**
- `dart_native_gen` codegen: parses ObjC headers or Java classes → generates Dart bindings
- Runtime: native C++ bridge calls `objc_msgSend` (iOS) or JNI (Android)
- Dynamic dispatch: method resolution at runtime via libffi + metadata

**Status:** Experimental/stalled. Last major release 2021. Alibaba's focus shifted. Superseded by official Dart FFI tooling (ffigen/jnigen).

**Key limitation:** Never reached parity with platform SDKs; manual binding writing still often required.

---

### 4.2 PyObjC (BridgeSupport metadata, Python)
**URL:** https://github.com/ronaldoussoren/pyobjc

**What it is:** Python ↔ Objective-C bridge using **BridgeSupport XML metadata format** (Apple's old system).

**How it works:**
- Metadata files (`.bridgesupport` XML) describe ObjC types, struct layouts, function signatures
- Tool: `gen_bridge_metadata` generates metadata from header files
- Runtime: ctypes + ObjC runtime introspection; lazy class wrapping via `objc.loadBundle()`
- Dynamism: Methods and properties discovered at runtime from metadata

**How it differs from NativeScript:**
- BridgeSupport is XML-based (human-readable but larger); NativeScript uses binary
- PyObjC relies heavily on **Apple's shipped BridgeSupport files** (now deprecated/abandoned by Apple in macOS 12+)
- Manual metadata fixups for tricky APIs via `.bridgesupport` override files

**Status:** Maintained for macOS, but **BridgeSupport deprecated by Apple**. PyObjC 12.1 (2025) dropped old metadata scans; now manually adds annotations for newer SDKs. Effectively in "maintenance mode."

**License:** MIT

**URL:** https://github.com/ronaldoussoren/pyobjc; https://pyobjc.readthedocs.io

---

### 4.3 rubicon-objc (BeeWare, Python)
**URL:** https://github.com/beeware/rubicon-objc

**What it is:** Lightweight Python ↔ Objective-C bridge using ctypes + ObjC runtime introspection (no pre-generated metadata, purely dynamic).

**How it works:**
- No metadata files; uses ObjC runtime's `objc_getClass()`, `class_copyMethodList()`, etc.
- Type annotations in Python: use ctypes primitives (c_int, c_float, c_char_p) or Rubicon types (NSInteger, NSString*)
- Runtime discovery: method signatures fetched on-the-fly via ObjC introspection

**Tradeoff:** Simpler (no build-time codegen), but slower method lookup (no caching).

**Status:** Maintained; active development (2024-2025). Part of BeeWare initiative.

**License:** BSD

---

### 4.4 Pyjnius / Chaquopy (Python on Android)
**URL:** https://github.com/kivy/pyjnius; https://chaquo.com

**What it is:** Python ↔ Java bridging via pure JNI reflection (no metadata, fully dynamic).

**How it works:**
- **Pyjnius:** ctypes-based; uses JNI to call `Class.forName()`, `getDeclaredMethods()`, etc. at runtime
- **Chaquopy:** Commercial Python runtime for Android; wraps Pyjnius with build tooling
- Dynamic dispatch: every method call goes through JNI reflection lookup
- No build-time codegen; type information inferred at call time

**Limitations:**
- Pyjnius requires native compilation (JNI stubs); incompatible with Chaquopy's pure-Python model
- Startup time: first access to a Java class incurs reflection overhead
- No IDE completion without manual stub files

**Status:** Pyjnius: maintained (Kivy team). Chaquopy: commercial, active.

**License:** Pyjnius: MIT

---

### 4.5 Unity AndroidJavaObject/AndroidJavaProxy (C# on Android)
**URL:** https://docs.unity3d.com/ScriptReference/AndroidJavaObject.html

**What it is:** Unity's high-level C# wrapper over JNI for dynamic Java interop.

**How it works:**
- Wraps JNI calls; provides `AndroidJavaObject` (instance wrapper) and `AndroidJavaClass` (class wrapper)
- Methods discovered at runtime via JNI reflection
- Caching optimizations: `AndroidJNIHelper` caches method IDs to speed repeated calls
- Type conversions: primitive types marshalled via ctypes-like bindings; objects wrapped in `AndroidJavaObject`

**Built on:** Low-level `AndroidJNI` static methods (direct JNI wrappers).

**Status:** Maintained by Unity; core platform API.

**License:** Proprietary (Unity)

---

### 4.6 JNA (Java Native Access)
**URL:** https://github.com/java-native-access/jna

**What it is:** Java library for dynamic C/native library calls via libffi (no JNI, no binding code).

**How it works:**
- Developer defines Java interface matching native function signatures
- Runtime: JNI stub uses libffi to call arbitrary C functions by address
- No metadata files; type information embedded in Java interface definitions
- libffi abstracts calling convention (cdecl, stdcall, etc.)

**Tradeoff:** Simpler (no build-time codegen), but slower than JNI (libffi → C call → Java return marshalling).

**Status:** Maintained; widely used in enterprise Java.

**License:** Apache 2.0/LGPL

---

### 4.7 Dart ffigen / jnigen (Static Code Generation)
**URL:** https://github.com/dart-lang/ffigen; https://github.com/dart-archive/jnigen

**What it is:** **Static code generation** for Dart ↔ C/Java bindings (contrast to NativeScript's dynamic).

**How it works:**
- **ffigen:** Parses C headers with clang AST → generates Dart FFI bindings (.dart code)
- **jnigen:** Parses Java JAR/source → generates Dart + C bindings (Dart calls C stubs, stubs call JNI)
- **Key difference from NativeScript:** All bindings pre-generated and compiled into app; no runtime metadata needed

**Trade-offs:**
- Pro: Faster calls (no runtime dispatch); smaller APK (generated code tree-shakeable)
- Con: Only publicly announced/curated APIs; can't access arbitrary Java/C on the fly

**Status:** Active development (2024-2026). Part of Dart platform.

**License:** BSD

**URL:** https://dart.dev/interop/java-interop

---

### 4.8 Node.js koffi / ffi-napi (Dynamic C FFI)
**URL:** https://github.com/Kode/koffi; https://github.com/node-ffi-napi/node-ffi-napi

**What it is:** Dynamic C FFI for Node.js (similar to JNA or libffi).

**How it works:**
- **koffi (3.2.0, active):** Fast dynamic C calls via libffi + V8 native bindings
- **ffi-napi (4.0.3, slow maintenance):** N-API wrapper over libffi (more portable but slower)
- Type definitions: JS objects describe struct layouts; functions called by address at runtime

**Status:** koffi actively maintained; ffi-napi stalled (N-API sandboxing overhead became limiting). Forks available (@napi-ffi/ffi-napi).

**License:** MIT/Apache 2.0

---

### 4.9 Godot GDExtension (Note: not a bridging system)
**Status:** Out of scope. Godot GDExtension is a plugin API for C++/Rust native modules, not a dynamic bridge to arbitrary platform APIs.

## 5. Trade-Off Analysis: Dynamic Metadata-Driven vs. Static Code Generation

### Dimension 1: API Coverage

| Approach | Coverage | Notes |
|----------|----------|-------|
| **Dynamic (NativeScript)** | ~100% of public APIs | All SDK classes, methods, properties auto-exposed; limited by `@objc` (Swift) and bytecode visibility (Java) |
| **Static (Dart ffigen/jnigen)** | Curated/announced APIs | Only what developer explicitly wraps; typical: 10-50% of SDK |

**Verdict:** Dynamic wins for coverage. Static requires ongoing maintenance as SDKs evolve.

---

### Dimension 2: Binary Size & Tree-Shaking

| Approach | APK Impact | Typings Package | Notes |
|----------|------------|-----------------|-------|
| **Dynamic (NativeScript)** | +2-5 MB metadata | 13.2 MB (iOS), 141 MB (Android) | Metadata embedded; all APIs included (hard to exclude). Types published separately. |
| **Static (Dart ffigen)** | Near zero for unused | ~1-10 MB generated .dart | Generated bindings compiled to native; tree-shaking removes unused code. Types bundled in app. |

**Verdict:** Static wins for shipping binary size. Dynamic's metadata is overhead, but separated from app (npm package).

---

### Dimension 3: Startup Time

| Approach | Cold Start Overhead | Typical Value | Notes |
|----------|-------------------|---|---|
| **Dynamic (NativeScript)** | Metadata decompression + MethodCache init | 100-300 ms | One-time on app launch |
| **Static (Dart ffigen)** | None | ~0-10 ms | All stubs pre-compiled |

**Verdict:** Static wins. Dynamic startup cost is amortized (happens once), but notable for games/CLI tools.

---

### Dimension 4: Per-Call Overhead

| Approach | Primitive Call | Object Call | Notes |
|----------|---|---|---|
| **Dynamic (NativeScript)** | ~1.5-2x native | ~2-3x native | Runtime marshalling via metadata signatures; libffi/JNI reflection lookup (cached) |
| **Static (Dart ffigen)** | ~1.0-1.2x native | ~1.2-1.5x native | Pre-generated stubs; no reflection; JNI method IDs compiled in |
| **Pure native (Swift/Kotlin)** | 1x (baseline) | 1x (baseline) | Reference point |

**Source:** NativeScript benchmarks (https://blog.nativescript.org/perf-metrics-universal-javascript-part1/); Dart benchmarks.

**Verdict:** Static is faster. Dynamic's runtime dispatch adds overhead, but acceptable for most UI apps (not tight loops).

---

### Dimension 5: Type Safety & IDE Completion

| Approach | IDE Support | Type Checking | Notes |
|----------|---|---|---|
| **Dynamic (NativeScript)** | Excellent (13.2 MB + 141 MB type packages) | TS strict mode supported | `@nativescript/types-*` provides full definitions; editor can resolve all APIs |
| **Static (Dart ffigen)** | Excellent (generated Dart interfaces) | Type-safe (Dart's strong typing) | Generated stubs are typed; ffigen ensures consistency |

**Verdict:** Tie. Both provide full type safety if type packages are up-to-date.

---

### Dimension 6: Maintenance Burden

| Aspect | Dynamic | Static |
|--------|---------|--------|
| **When SDK updates** | No app code changes; metadata auto-updated on SDK bump | Must re-run generator; commit new binding files; possible manual fixes |
| **Breaking API changes** | Breakage happens at runtime (call fails) | Breaks at compile time (type error) |
| **Plugin ecology** | Zero-binding plugins (just TS code) | Must ship pre-generated binding files or generator script |

**Verdict:** Dynamic wins for maintenance. Static requires more manual bookkeeping.

---

### Dimension 7: Debuggability

| Approach | Stack Traces | Introspection | Notes |
|----------|---|---|---|
| **Dynamic (NativeScript)** | Clear JS↔Native boundaries | Metadata available at runtime; can inspect method signatures | Good for debugging marshalling errors |
| **Static (Dart ffigen)** | Generated stubs in stack; requires symbol maps | Type info only; can't discover APIs at runtime | Still debuggable, but less introspection |

**Verdict:** Slight edge to dynamic (more runtime info).

---

### Dimension 8: Platform Constraints (AOT/JIT/App Store)

| Constraint | Dynamic Impact | Static Impact | Notes |
|---|---|---|---|
| **iOS App Store (no JIT)** | Not relevant (metadata ≠ JIT code) | Not relevant (ffigen generates native code) | Both fine. |
| **Android (DEX/JIT)** | MethodCache uses JNI method IDs (compiled); works with DEX | Works with DEX | Both fine. |
| **Hermes (JS engine)** | NativeScript supports; metadata still used | N/A (Dart doesn't use Hermes) | Different ecosystems. |

**Verdict:** No significant difference; both comply with platform constraints.

---

### Dimension 9: Isolation / Thread Models

| Model | Dynamic | Static |
|---|---|---|
| **JS thread ↔ Native thread** | Metadata aware; can marshal across threads; SBG generates thread-safe stubs | Generated stubs are also thread-safe (standard JNI) | Both handle threading. |
| **Multiple JS engines (Hermes, QuickJS, etc.)** | NativeScript 8.9+ supports swappable engines; metadata transport is engine-agnostic | Ffigen generates Dart code; not reusable across engines | Dynamic is more portable. |

**Verdict:** Slight edge to dynamic (simpler multi-engine support).

---

### Dimension 10: Surprises & Edge Cases

**Dynamic (NativeScript):**
- **Swift limitation:** Only `@objc` methods visible; modern Swift-only APIs (async/await, actors) not bridged
- **Kotlin edge case:** Suspend functions don't map to JS Promises automatically
- **Generics erasure:** `ArrayList<String>` → `ArrayList` in JS; type information lost at runtime
- **Metadata size creep:** New SDK frameworks added → metadata grows; hard to exclude

**Static (Dart ffigen):**
- **C header brittleness:** Macro definitions, conditional compilation can confuse clang parser
- **Regeneration burden:** Adding one new API requires full recompile and re-commit of binding files
- **Forward compatibility:** Old generated bindings can break if API signature changes (must regenerate)

## 6. Surprises & Corrections to Common Beliefs

1. **"Dynamic bridging is slow"** — Yes, 1.5-2x native calls is real, but acceptable for UI apps. Games with tight loops should prefer static.

2. **"NativeScript metadata is huge"** — It's 2-5 MB in the APK (small). The 13.2/141 MB type packages are development-only (npm), not shipped.

3. **"Swift APIs are inaccessible"** — Only **public** (non-`@objc`) Swift is inaccessible. Most UIKit is bridged because it's ObjC-based. Modern SwiftUI APIs are largely inaccessible.

4. **"BridgeSupport is alive"** — False. Apple abandoned it in macOS 12 (2021). PyObjC switched to manual metadata in 2025.

5. **"Static code generation is zero-overhead"** — False. Generated stubs still marshal types, just at compile time. Primitives: ~1.0-1.2x native (still overhead).

6. **"Android metadata is ASM-based"** — Partially true. NativeScript uses **Apache Commons BCEL** (bytecode engineering library), not pure ASM. Both are bytecode introspection tools.

7. **"You can't access arbitrary Java from NativeScript"** — False. Metadata doesn't limit API access; it optimizes lookup. Any Java class can be dynamically loaded via `java.lang.Class.forName()` at runtime.

8. **"Kotlin generics work transparently"** — Mostly true, but SBG's "reification" only applies to SBG-generated classes. Regular reflection of `List<String>` loses type info.

## 7. Open Questions (Unverified)

1. **Binary metadata format internals:** Exact layout of `metadata-<arch>.bin` (iOS) and `treeNodeStream.dat` (Android) — no specification found. Reverse-engineering needed.

2. **Metadata compression algorithm:** What compression (if any) is used for metadata? Mentioned as "minimal" but no specifics.

3. **MethodCache eviction policy:** On Android, how does the MethodCache handle memory pressure? LRU? Fixed size?

4. **SBG C++ class support:** Can SBG generate stubs for C++ classes (via Objective-C++ wrappers)? Documentation only mentions Java/ObjC.

5. **Kotlin coroutine bridge:** Is there a roadmap for native Kotlin suspend → JS Promise mapping in NativeScript 9.x+?

6. **Swift-ObjC interop in metadata:** Does the iOS metadata-generator parse Swift's generated ObjC headers, or does it require explicit `@objc` annotations?

7. **A/B testing of call overhead:** Published NativeScript benchmarks exist (blog.nativescript.org), but head-to-head comparison with React Native or Flutter native calls not found.

8. **Type definition update frequency:** How often are `@nativescript/types-*` npm packages updated when iOS/Android SDKs ship? Quarterly? On-demand?

---

## Conclusion

NativeScript's metadata-driven dynamic bridge is a pragmatic **coverage + automation** tradeoff: you get 100% of native APIs with zero binding code, at the cost of ~1.5-2x call overhead and large type packages. The Static Binding Generator hybrid model is a clever optimization for extensibility (JS subclasses of native classes). For Dart, static code generation (ffigen/jnigen) trades API coverage for startup speed and smaller binaries. Both approaches are actively maintained and suitable for production use; choice depends on whether coverage or performance matters more for your use case.
