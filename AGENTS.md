# AGENTS.md — working in the bindsmith repository

`CLAUDE.md` is a symlink to this file. These rules apply to every coding agent and every human contributor.

## What this project is

`bindsmith` is a Dart command-line tool that reads one `bindsmith.yaml` and generates Dart bindings for native APIs on all six Flutter platforms (Android, iOS, macOS, Windows, Linux, Web). It orchestrates the official generators through their library APIs (ffigen, swiftgen, jnigen, winmd, dart-dbus) and adds a TypeScript `.d.ts` driver for Web, a unified IR with fixup passes, review markers, dependency resolution with a lockfile, and a verification matrix.

Read in this order: `plan.md` (what is left to build, per task complexity and acceptance), `done.md` (what is already built, with the implementation notes), `research.md` (why, with sources), `docs/research-raw/` (raw evidence and fact-check logs). Do not re-derive decisions recorded in `docs/adr/`.

## Layout

```
packages/bindsmith/           generator: bin/, lib/src/{cli,config,deps,ir,passes,drivers,emit,verify}, tool/ts_sidecar/
packages/bindsmith_runtime/   tiny runtime used by generated code (annotations, dispatch, errors); no dependency on the generator
fixtures/                     workspace package: fixture inputs (dts/, c/, jvm/, swift/, …), generated outputs under lib/generated/, runners in bin/, generated build hooks in tool/ — must always analyze clean
schema/                       bindsmith.schema.json, exported from lib/src/config/schema.dart
docs/                         research (EN + RU copies), ADRs
```

## Toolchain and commands

The toolchain is installed with [mise](https://mise.jdx.dev) from `mise.toml` (Dart 3.13, node 24, Temurin JDK 21). libclang is the one thing mise does not manage: Xcode on macOS, `libclang-dev` on Linux, LLVM on Windows.

```bash
mise trust && mise install                        # once per machine
mise run setup                                    # dart pub get + npm ci for the .d.ts sidecar
mise run check                                    # format check, dart analyze --fatal-infos, fixtures analyze
mise run test                                     # dart test (both packages) + node --test (sidecar)
```

Direct equivalents when you need one step:

```bash
dart format packages fixtures
dart analyze --fatal-infos
(cd packages/bindsmith && dart test)
(cd packages/bindsmith_runtime && dart test)
(cd packages/bindsmith/tool/ts_sidecar && node --test)
UPDATE_GOLDENS=1 dart test                        # from a package dir, to rewrite golden files after an intended change
dart run packages/bindsmith/bin/bindsmith.dart --help
```

Golden helpers (`expectGolden`, `containsCode`) live in `packages/bindsmith/test/golden.dart`; golden paths are relative to the package root. The `.d.ts` end-to-end test (`test/drivers/dts_test.dart`) spawns `node` on the sidecar and rewrites `fixtures/lib/generated/greeter/` under `UPDATE_GOLDENS=1`, so run `mise run setup` first.

The JVM tests (`test/drivers/jvm_test.dart` for the Java fixture, `test/drivers/kotlin_test.dart` for the Kotlin one) need a JDK on `PATH` (`mise install` provides Temurin 21) and, the very first run, network access: jnigen builds its API summarizer with Gradle into `.dart_tool/jnigen/ApiSummarizer.jar` at the repository root, and every later run reuses that jar. jnigen also needs `package:jni` to resolve — but `jni` declares `flutter: '>=3.35.6'` in its `environment:`, so a pure-Dart `dart pub get` cannot add it to this workspace. `JniProject` (`test/jvm_toolchain.dart`) gets around that without touching the workspace: it writes a throwaway package that depends on bindsmith by path, resolves it with `flutter pub get` (mise installs Flutter), and runs jnigen under that package config with the repository root as the working directory, so the summarizer jar is still shared. The Kotlin suite also compiles the fixture with `kotlinc`, builds `libdartjni` once with `dart run jni:setup` (CMake, also from mise) into `.dart_tool/bindsmith/jni-<version>/`, and calls the generated binding on a desktop JVM through `Jni.spawn` — keep that runtime check, it is the only one that sees a `suspend` resumed on another thread or a listener implemented in Dart. Without Flutter or a JDK both suites read the committed bindings in `test/drivers/goldens/` and still run every IR expectation, since `jvmToIr` is pure; those goldens live under `test/` and not under `fixtures/` for the same reason — `fixtures` must stay pure Dart and analyze clean. Never let jnigen run where `package:jni` does not resolve: it calls `exit(1)`, which ends the test runner instead of failing a test, and that is why `JvmDriver.load` checks first and throws.

The config loader (`lib/src/config/`, tested by `test/config/config_test.dart`) keeps one JSON Schema and uses it twice. `schema.dart` holds the schema as a Dart map; `bindsmithSchemaJson()` writes it to `schema/bindsmith.schema.json` for an editor's YAML language server, and `validateAgainstSchema` walks a parsed YAML tree against the same map — so what an editor underlines and what the loader rejects cannot drift. That validator understands only the keywords the document actually uses, and a test walks the schema from the other side to fail on a keyword it would silently ignore; when you add one to the schema, teach the validator about it in the same change. Loading runs in two passes for a reason: the schema settles shape and nothing proceeds past a shape that did not hold, because everything after it reads the tree as the schema describes it. Meaning is then the loader's job, and it reports *every* problem rather than the first — that a platform names a driver or inherits from one that is configured directly, that `headers:` was not written under a `jvm` driver, that a Maven coordinate parses. The `_accepts` table is the load-bearing part: without it a key under the wrong driver would simply do nothing, which is rule 3's silent drop wearing a config file. Errors carry line and column through `package:source_span`, and the `bindsmith.yaml` published in `report.html` loads verbatim as one of the tests, so the documentation and the loader cannot disagree. The same schema writes `docs/config.md`: `bindsmithConfigReference()` (`lib/src/config/reference.dart`) walks it and the page is committed as a golden, so adding a key without regenerating fails `test/config/reference_test.dart` rather than leaving the reference quietly wrong. Prose that the schema cannot carry — which keys a driver actually reads, why a path must be under `lib/` — lives in the hand-written pages beside it (`getting-started.md`, `platforms.md`, `fixups.md`, `upgrading.md`), which GitHub Pages serves from `docs/` with a one-line `_config.yml`.

`Layout` (`lib/src/emit/layout.dart`) is the only thing that knows where a generated file goes, and everything that needs a path asks it rather than joining one. That is not tidiness: three things have to agree about the same file and none of them can see the others — the driver is handed an output path and an asset id before any content exists, the facade imports each binding by a path relative to itself, and `hook/build.dart` declares the asset that the binding's `@DefaultAsset` names. A binding whose asset id no hook declares fails at the first call with nothing to point at, so all three are derived from one another here. Its paths are POSIX and relative to `bindsmith.yaml`, which is at once a correct import string and a path `dart:io` accepts on Windows, so nothing converts between the two. Iteration is over `Platform.values`, never over the config's own key order, so rewriting the config file in a different order cannot change a generated file (rule 6). The loader enforces what the layout depends on: generated Dart must be under `lib/`, because a file anywhere else has no `package:` URI and therefore no asset id.

`emitBuildHook` (`lib/src/emit/build_hook.dart`) writes one `hook/build.dart` for every platform that configured `build:`, because a package may only have one and it runs once per target — hence one `targetOS` guard per platform rather than one file per platform. Both emitted hooks are committed under `fixtures/tool/build_hook/` so that `dart analyze --fatal-infos fixtures` type-checks them against the real `hooks`, `code_assets`, `native_toolchain_c` and `native_toolchain_cmake` APIs, which is why those four are dev dependencies of `fixtures`. Keep them there and not under `lib/` (a file there may not import a dev dependency) and above all not at `fixtures/hook/build.dart`, where they would run during every fixture build and try to compile sources that do not exist. A golden alone would only catch our own edits; the analyzer is what catches an upstream rename.

`emitAndroidGlue` (`lib/src/emit/android_glue.dart`, tested by `test/emit/android_glue_test.dart`) writes `android/bindsmith.gradle` and `android/bindsmith-rules.pro` beside a package's `android/build.gradle`, never into it: that file and the pubspec are the author's, so the script's header says what to add to them (`apply from:`, `ffiPlugin: true`) instead. The keep rules are load-bearing — jnigen finds each class by name at run time, R8 cannot see that, and the failure shows up only in a release build — so they are derived from the classes the IR says were bound, never from the pull list, and the tests emit them from the JVM driver's committed IR snapshots rather than from hand-written IR.

The command line (`lib/src/cli/runner.dart`, tested by `test/cli/cli_test.dart`) is one file, and `bin/bindsmith.dart` does nothing but hand it the real streams and set `exitCode`. `runBindsmith(args, out:, err:, workingDirectory:)` returns the exit code rather than calling `exit` and writes through injected `StringSink`s, which is why every CLI test runs in-process against a throwaway project directory instead of spawning a Dart VM and mutating `Directory.current`. Keep it that way when you add a command. Exit codes are `sysexits(3)` — 64 usage, 65 a config that was read and cannot be used, 66 a missing file, 70 generation itself — and the split is the reason to have them: a script can tell "fix your config" from "the generator broke". `generate` is the only place where the whole pipeline is assembled (layout → driver → passes → facade → build hook), and it dispatches `c`, `objc`, `swift`, `jvm` and `dbus`; the other three drivers each still need something the configuration cannot say or resolve, so they raise an error naming the platform and the driver rather than generating nothing and reporting success. Two tests there are load-bearing and easy to weaken: the `init` template is checked by loading it through `loadBindsmithConfig`, not by comparing text, and one test runs `generate` twice and compares the bytes (rule 6).

Every command is the same load with a different destination, which is why `_emit` takes an output root: a driver writes its binding by construction, so a command that only reads (`dump`, `diff`, `explain`, and `generate --check`) points the drivers at a directory that is deleted afterwards and never touches the project. Keep it that way — before this, `dump` wrote a binding into the tree as a side effect of printing. `generate --check` is the whole run again into that throwaway directory compared against what is committed, so it is safe on a clean checkout, and because the scratch path differs every time, a passing check also proves no generated file embeds where it was generated (the bug that put a `/Users/…` walk into the Objective-C glue). `diff` compares an earlier `dump` on *shape*, not on JSON: markers and doc comments move constantly and a changed signature is what breaks a caller. It exits 1 when anything differs, as `diff(1)` does, and so does `--check`. `watch` takes its stamps before a run rather than after, or a header edited while generation is in flight is absorbed into the baseline and never rebuilt; it survives a configuration that does not parse, because that is the state a file is in while someone edits it.

The Maven resolver (`lib/src/deps/maven.dart`, tested by `test/deps/maven_test.dart`) is bindsmith's own, and that is deliberate: jnigen resolves Maven by writing a stub Gradle project and running `gradlew`, which is driving a tool through its console (rule 1) and produces nothing that can be pinned. `Pom.parse` is a pure function of one string with its own unit tests, the way a pass is, and `MavenResolver` is the impure half around it; `MavenFetch` is injectable, so every resolution test runs against an in-memory repository and only the one test that reaches Maven Central needs a network. That test carries the `network` tag declared in `dart_test.yaml` (`dart test -x network` skips it) and also skips itself when the host cannot look up the host name — the tag is for choosing, the self-skip is for being offline. Two things there are load-bearing. Element lookup is by direct child everywhere, because a POM also carries `<dependencies>` inside `<build><plugins><plugin>` and those belong to the build, not to any consumer. And `repositories` is a list searched in order rather than one URL, because a real Android artifact proved one is not enough: `androidx.annotation:annotation-experimental` comes from Google's Maven and the `kotlin-stdlib` it needs only from Central. Version ranges, `LATEST`/`RELEASE` and `-SNAPSHOT` are refused by name, since each makes one coordinate mean different bytes on different days and there is nothing honest to put in a lockfile. The download cache mirrors the repository layout, so it is itself a Maven repository and a second run over it touches no network.

`bindsmith.lock` (`lib/src/deps/lockfile.dart`, written and checked by the `resolve` command) is what that cache is pinned against: `version: 1` and a section per kind of dependency, each a list of `coordinate` / `extension` / `sha256` sorted by coordinate, so reordering the configuration cannot rewrite the file (rule 6). What it leaves out is deliberate. It does not name the repository that served the bytes — once the digest matches, where they came from does not change what you compiled against, and recording it would churn the lock whenever a mirror is added. It does not say which platform asked, because a coordinate names the same bytes whoever wanted it. And `lockKinds` refuses a section whose resolver has not landed rather than carrying it through, so a typo cannot look like a working lock. `lockKinds` is `{maven, npm, nuget}`; Maven sources jars pin as `g:a:v:sources` rather than a `classifier:` field. `parseLockfile` reports every problem with a line and a column the way the config loader does. The digest is the one field YAML can get wrong on its own: a hex digest of nothing but decimal digits resolves to a number — an integer, or a float once it outgrows one — and so does every digest in a lock written before bindsmith started quoting them. So a non-string scalar under `sha256` is read back from `span.text` rather than refused, and the value is then checked against `^[0-9a-f]{64}$`; the check is what makes that fallback safe, since it is handing back whatever the file said. Uppercase is refused deliberately: it would never equal a freshly computed digest and would be reported as changed bytes on every run, sending the reader after a mirror that is fine. bindsmith still writes the digest quoted, because a build script reading the lock with some other YAML library hits the same trap with no such fallback. A coordinate whose bytes disagree with the lock is a hard error naming it and never a rewrite: a released artifact does not change, so either the lock was edited or something is serving other bytes under that name. `--offline` installs a `MavenFetch` that throws, which is exactly the question — a resolve the cache can answer never calls fetch at all. `file:` repository URLs are accepted alongside `https:` (Gradle spells the same thing `maven { url = uri("file:///…") }`), which is also what lets `test/cli/cli_test.dart` publish two artifacts into a temporary directory, resolve, delete the repository and resolve again offline, exercising the real resolver with nothing injected. Plain `http:` stays refused; do not widen that.

The Objective-C tests (`test/drivers/objc_test.dart`) only generate on macOS: ffigen adds `-x objective-c` and the `xcrun --show-sdk-path` sysroot itself, so no other host can parse the headers. On Linux and Windows the test reads the committed binding from `fixtures/lib/generated/counter/` and runs every IR expectation against it, because `objcToIr` is pure; the checks that need selectors (which only the ffigen AST knows) are skipped there.

The Swift tests (`test/drivers/swift_test.dart`) are macOS-only for a second reason on top of the Objective-C one: swiftgen shells out to `swiftc` and to the Swift symbol graph extractor before ffigen ever runs. Elsewhere the committed binding under `fixtures/lib/generated/greeter_swift/` is read and the pure `swiftToIr` expectations still run. Two limitations of swift2objc 0.3 are load-bearing for the fixture and must not be "fixed" by widening it: a generic Swift type produces an `@objc` wrapper that does not compile, so `Box<T>` is excluded through the pull list; and a method with an array parameter (`greetAll(names: [String])`) is dropped with nothing but a `SEVERE` log record, which is why `SwiftDriver` keeps swiftgen's logger and turns those records into `dropped` markers.

Both suites end with a test that builds the fixture into a real library and calls the committed binding against it, through `fixtures/bin/counter_objc.dart` and `fixtures/bin/greeter_swift.dart` spawned as separate processes; off macOS they skip. Keep them, and add to them rather than to the IR expectations when the failure being guarded against is a runtime one — every Objective-C mistake is: a selector that does not exist fails at the call, a Dart-implemented protocol is only implemented once the callee dispatches to it, a block invoked off the isolate's thread crashes, and an `NSError**` is invisible in the Dart signature. The Swift runner exists for three more that the analyzer cannot see either: the mangled class name only resolves if the module really is named `GreeterKit`, a Swift struct only crosses as the wrapper class swift2objc writes around it, and an `async` method arrives as a completion handler that Swift calls from its own executor thread, so it needs `ObjCBlock_….listener` rather than `fromFunction`. The Swift library is two `swiftc` passes around one `clang`: `swiftc` emits the Objective-C header the generated glue imports, the glue compiles against it, and its object file links back into the same module so one dylib carries both — which also makes the fixture build the only check that the P7-1 bridge emitter writes Swift a compiler accepts. `ObjcDriver` rewrites the glue's `#import` to the header's own basename for the same reason `SwiftDriver` rewrites it to `<Module>-Swift.h`: ffigen writes a path from the generated file to the header it parsed, which for an absolute entry point walks through `/Users/…` and is neither reproducible (rule 6) nor buildable anywhere else.

`SwiftDriver` hands swiftgen its own temporary directory (`tempDirectory:`), because that is the only way to keep the `<module>.symbols.json` Swift symbol graph after generation: swift2objc deletes a directory it created itself, and the symbol graph is where the signature of a dropped declaration survives (swift2objc's diagnostics say *that* something was lost, not *what*). Two knobs feed a generated bridge back through the same pipeline: `objcCompatibleSources` are Swift files that are already `@objc` and therefore skip swift2objc and go straight to `swiftc` (swiftgen's `ObjCCompatibleSwiftFileInput`), and `objcCompatibleTypes` names the classes in them so the inclusion visitors keep them. ffigen writes its Objective-C glue with an `#import` pointing into that temporary directory, so the driver rewrites the line to `<Module>-Swift.h` — the header Xcode generates for a shipped plugin — which is both correct for consumers and the reason the `.m` golden is reproducible (rule 6).

The Kotlin bridge tests (`test/emit/kotlin_bridge_test.dart`) need `kotlinc` (mise installs Kotlin 2.4.20) and skip without it; the coroutines jar they compile against ships inside the Kotlin distribution, so nothing is downloaded. Their IR is hand-written rather than produced by `JvmDriver`, so they need nothing but `kotlinc`; `test/drivers/kotlin_test.dart` is where the driver's own IR goes through the emitter and the result is compiled. Every `native` string in the hand-written IR is a signature `javap` prints for the compiled fixture, and the last test closes the loop from the other side by compiling the emitted bridge against `fixtures/jvm/ktgreeter` — that is what proves the generated Kotlin is valid.

The C facade tests (`test/emit/facade_c_test.dart`) read the C driver's committed IR snapshot instead of running ffigen, so they need no libclang and run anywhere. The split they exercise is the one to keep: `cFacadePass` rewrites dart:ffi types into the API the facade offers and leaves the dart:ffi spelling in `TypeRef.native`, and the emitter reads that `native` to decide how a value crosses. Neither half parses the other's output, and the pass stays a pure `List<Decl> -> List<Decl>` with its own unit cases. The last test builds `fixtures/c/geometry/geometry.c` into a shared library with whichever of `cc`, `clang` or `gcc` is on `PATH` and runs `fixtures/bin/geometry_facade.dart` against it; that call is the only thing that catches an arena freed too early, a `Pointer<Char>` read as UTF-16 or an enum passed as its index, all of which compile. It skips on Windows and where no C compiler is found. The runner opens the library with `DynamicLibrary.open` before the first call, because `@Native` resolves through the asset id, then a registered resolver, then the process, and a `dart run` has no code asset.

Two things about the C facade are easy to get backwards. A struct is *not* native memory: `ffi.Struct.create` lays one out on the Dart heap, so a facade struct is garbage-collected and has no `dispose`, while the opaque handle beside it on the same page does — do not unify them. And a struct passed by pointer is an arena copy that is read back field by field after the call (P6-4d), because dart:ffi copies a struct into a pointer but has nothing that copies one out; a callee that *keeps* the pointer still outlives it, which is what the marker on those calls says. That one-way copy is also why a struct whose field is a pointer gets no constructor and no setter for that field: the facade could only fill it from an arena that is already gone.

Every test suite that waits on an external toolchain — Swift, Objective-C, JVM, and the winmd vtable check, which spawns `dart run` — carries `@Timeout(Duration(minutes: 5))` on its library directive (the Kotlin suite ten, since its first run resolves a Flutter project and builds `libdartjni`). The 30-second default is not a timeout on those, it is a load test of the host: on a busy machine `swiftc` and libclang blow through it and the suite fails for a reason that has nothing to do with the code. Add the annotation to any new suite that shells out.

The Windows tests (`test/drivers/winmd_test.dart`) run everywhere, because `package:winmd` is a pure-Dart metadata reader and `emit/win32.dart` writes text. There is no upstream generator for Windows — winmd reads, it does not emit — so bindsmith writes the dart:ffi binding itself, and the task splits into a driver (metadata → IR) and an emitter (IR → Dart) that meet only in the IR. The real `Windows.Win32.winmd` is a ~10 MB NuGet asset, so the fixture is built in memory instead: `test/drivers/winmd_sample.dart` writes a small assembly with `MetadataWriter`, which keeps the input readable and commits no binary. Two things there are load-bearing. The module version id is fixed rather than generated, or the assembly would differ byte for byte between runs (rule 6). And a custom attribute's fixed arguments are decoded against the constructor `MemberRef`'s signature, so an attribute written with an empty signature reads back as garbage — `_attributeCtor` takes the argument types for that reason.

`WinmdDriver` is given a pull list and follows every type its signatures reach, so a struct nested three deep still lands in the IR; a name that is not in the metadata raises `ArgumentError` rather than returning nothing. A symbol `package:win32` already binds is not regenerated: `covered` maps it to the identifier that package exports, the declaration is kept and marked `dropped` with `reexportedFrom(library)`, and the emitter turns that exact marker into one `export … show` — driver and emitter share the function, so nothing sniffs strings. The generated COM shape follows `package:win32` (a class over `IUnknown` holding a `VTablePointer`, a `base$`-chained vtable struct, `asFunction` per slot) so interfaces from either side interoperate. `fixtures/bin/win32_vtable.dart` is what proves that layout: it fills a raw buffer with known addresses, reads the generated struct back, and fails if a slot moves — a check that runs on any host and catches what a text expectation cannot. That is also why `fixtures/` depends on `win32`.

The C++ shim tests (`test/emit/cpp_shim_test.dart`) compile `fixtures/cpp/greeter` together with the generated `shim.g.cc` into a shared library using whichever of `clang++` or `g++` is on `PATH`, then call it through `dart:ffi` — that runtime check is the only thing that proves the exception guard actually stops an exception at the `extern "C"` boundary, so do not replace it with a text expectation. It skips on Windows and where no C++ compiler is found. The IR it emits from is hand-written on purpose: bindsmith does not parse C++, so a shim is described by configuration, and `TypeRef.native` carries the C++ spelling (`const std::string&`) that the emitter maps.

The web tests (`test/drivers/dts_test.dart`) compile `fixtures/bin/greeter_web.dart` with `dart compile js` **and** `dart compile wasm`, and that pair is load-bearing: js_interop legality is decided by the web compilers, not by the analyzer, and the two back ends disagree about what they will lower. The bug that check exists for is already in the emitter's history — a top-level `external` member needs its own `@JS()`, because `@JS()` on the library supplies the namespace but marks nothing as interop, and `dart analyze` reports none of it. The entrypoint touches every generated member on purpose; a tree-shaken member is never lowered and so is never checked. Keep the split the same way the C facade keeps it: `dtsFacadePass` invents the Dart-side types JavaScript does not have and the binding keeps saying exactly what the `.d.ts` said. So an inline `'formal' | 'casual'` becomes an enum named after its declaration site and marshalled as `.value`, and a callback parameter takes a Dart function converted with `.toJS` — while a callback coming *out* of JavaScript stays `JSFunction`, because `.toJS` goes one way only and each call to it makes a new `JSFunction`, which is why the conversion carries a verify marker rather than being hidden.

The TypeScript sidecar depends on `typescript` **6.x** (exact pin in `tool/ts_sidecar/package.json`). `typescript@7` on npm is the Go-native compiler and ships no JavaScript Compiler API, so it cannot be used. CI runs the same steps on macOS, Ubuntu and Windows (`.github/workflows/ci.yml`).

## Rules that are not negotiable

1. **Upstream is driven through library APIs, never by parsing console output.** Each upstream generator gets exactly one adapter file under `lib/src/drivers/<name>/`. Pin upstream to one major (`^22.0.0`, not `>=22`). When an adapter breaks, fix the adapter, do not spread `try/catch` into passes or emitters.
2. **Verify API names against the pub cache, not memory.** ffigen 22 and jnigen 1.0 rewrote their APIs in 2026. Before calling an upstream class, open its source under `~/.pub-cache/hosted/pub.dev/<pkg>-<version>/lib/`.
3. **No silent drops.** Anything a driver or pass cannot map becomes a `Marker` on the IR (`verify` or `dropped`, with a reason) and shows up in `bindsmith dump` and `bindsmith verify`. Losing a symbol quietly is a bug.
4. **Passes are pure functions** `List<Decl> → List<Decl>` with unit tests on hand-built IR. Emitters read IR only; they never reach into driver internals.
5. **Golden tests for every emitter.** Output is `dart format`-ed before comparison. Generated fixture output is committed and must pass `dart analyze --fatal-infos fixtures`.
6. **Deterministic generation.** Same inputs and lockfile produce byte-identical output; CI runs `generate --check`.
7. **Lean code.** No speculative abstractions, no interface with one implementation, no config for a value that never changes. Fewest files that stay readable. Prefer the standard library over a new dependency; adding a dependency needs a one-line justification in the PR.
8. **Never weaken:** input validation at the config boundary, error messages that say what to fix, cross-platform path handling (`package:path`), Windows line endings in golden comparison (normalize `\r\n`).
9. **The human is the only author.** No agent adds a `Co-Authored-By` trailer, a "Generated with …" line or itself as author to a commit, merge or PR — whatever its harness defaults to.

## How to pick work

Work risk-first. `plan.md` rates every task by complexity (C1 easy … C5 hard) and lists the execution order; take the highest-complexity unfinished task whose prerequisites are done. `plan.md` holds only open work — when a task is finished, move its table row and its detail paragraph to `done.md` in the same change, so the plan is always a list of what is left and `done.md` the record of what is built.

Definition of done for any task: `dart analyze --fatal-infos` clean; `dart format` clean; tests added or updated and passing; fixtures analyze clean; the task moved to `done.md`; if behavior is user-visible, `README.md` or `docs/` updated.

## Style

- Dart 3.13, `lints/recommended` plus the strict flags in `analysis_options.yaml`. Sealed classes for IR variants, records for small tuples, `final` by default.
- Names: `Decl`, `TypeDecl`, `Member`, `TypeRef`, `Marker` in IR; `<Name>Driver`, `<Name>Adapter`, `<Name>Emitter`, `<name>Pass`.
- Generated files end with `.g.dart` and start with `// GENERATED BY bindsmith — do not edit.` Every other file bindsmith writes carries the same line, written by the generator and never added by hand: the Objective-C glue (`.g.m`, prepended by the driver because ffigen's `preamble` reaches only the Dart file), the swift2objc wrapper (through `SwiftWrapperFile.preamble`), `bindsmith.lock` (`#`), `docs/config.md` (`<!-- -->`) and the JSON Schema (a top-level `$comment`, since JSON has no comments).
- Documentation travels with the declaration. A driver puts the source's own doc comment into `docs`, as Markdown, and nothing else: ffigen's selector-name fallback (`/// alloc`) and jnigen's ``from: `…` `` line and release note are stripped, Javadoc's `{@code}`/`{@link}` become Markdown, JSDoc's `{@link X}` a dartdoc `[X]`, matched `@param` into `Param.docs`, `@returns` prose as `Returns …` in member docs, and `@deprecated`/`@since` an `Availability`. Doxygen `@param`, Kotlin KDoc `@param`, and Swift `- Parameter` follow the same split. KDoc is read from `.kt` files by `kdocs` in the JVM driver; jnigen's summarizer does not carry it. ffigen parses plain `//` and `/* */` comments as well (`sourceComments`), and a Swift declaration swift2objc kept takes its docs from the symbol graph, because the wrapper carries none. The raw upstream binding keeps what upstream wrote; the IR, the facade and the bridges get the source's text.
- Commit messages: conventional commits (`feat(ir): …`, `fix(drivers/dts): …`, `docs(plan): …`). One logical change per commit. Do not commit `pubspec.lock` (workspace) or `node_modules`.
