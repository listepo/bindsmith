### Phase 1 — Config, IR, first vertical slice: C driver (1.5 weeks) — C4

- **P1-1** `config/`: `loadBindsmithConfig(source, sourceUrl:)` → `BindsmithConfig`, or `ConfigException` carrying **every** problem, each formatted by `package:source_span` with its line, column and the offending line underlined. The schema is not written twice: `schema.dart` holds one JSON Schema map that `bindsmithSchemaJson()` exports to `schema/bindsmith.schema.json` (committed, golden-tested) *and* that a small validator walks the parsed YAML against, so what an editor's language server underlines and what the loader rejects cannot drift. The validator handles only the keywords that document uses; a test walks the schema from the other side and fails on a keyword it would silently ignore. Loading is two passes and the split is deliberate: the schema settles shape (spelling, types, which keys exist) and nothing proceeds past a shape that did not hold, then the loader settles meaning, which JSON Schema expresses badly — that a platform names a driver or inherits from one that is configured directly, that `headers:` was not written under a `jvm` driver, that `include: {classes:}` means nothing to the C driver, that a Maven coordinate parses (reusing P3-2, so a typo is caught at load rather than at download). The `_accepts` table is what makes a mis-keyed platform an error instead of a key that quietly does nothing — rule 3 applied to configuration. `bindsmith schema` as a *command* lands with the CLI in P1-4; the export function and the committed file are here. The configuration published in the report loads verbatim as one of the tests, so the docs and the loader cannot disagree.
- **P6-1** `ir/` as in §3, with `toJson` for snapshot tests (built in step 1 of §5, before this phase's driver).
- **P1-2** C driver (`lib/src/drivers/c/c_driver.dart`): `CDriver(platform:, headers:, compilerOptions:, include:, assetId:, preamble:).load(workingDirectory:, output:, libclangDylib:, logger:)` builds `FfiGenerator(input: Input(entryPoints:, include:, compilerOptions:), output: Output(dart: DartOutput(path:), style: NativeExternalBindings(assetId:), preamble:), visitors: [Visitor(func:, struct:, union:, enumClass:, global:, macroConstant:, typealias:)])` and `await generate(logger:, libclangDylib:)`. Verified against ffigen 22.0.0 source: the public AST exposes `usr`, `originalName`, `name`, `isIncluded` and parameter names but **no types**, so the visitor records C names, field/constant names, variadic-ness and the pull list, and the pure `cToIr` reads the signatures back from the generated Dart with `package:analyzer` (syntax only). Everything in ffigen is `isIncluded = false` by default: entry-point headers are selected with `Input.include`, symbols with the visitor, typedefs with `TypealiasInclude.ifUsed` so they follow their users. `TypeRef.native` keeps the dart:ffi spelling (`ffi.Pointer<ffi.Char>`), `Member.value` the enum/macro literal; wrappers ffigen writes for enum-taking functions are the API and the `_name` externals behind them are skipped. Markers: variadic functions (fixed arguments only), unions (shared storage), enums (implementation-defined width), function-pointer typedefs (`Pointer.fromFunction`/`NativeCallable`). Test `test/drivers/c_test.dart` (11 cases): IR golden, committed binding `fixtures/lib/generated/geometry/c.g.dart`, a pull-list run and a libclang-free `cToIr` case. Deferred: an abstract `Driver` interface (one implementation per platform, decided at P1-4 when the CLI needs the dispatch) and facade marshalling over C (P6-4b).
- **P1-3** `emit/layout.dart` + `emit/build_hook.dart`. The layout is a value, not a step: `Layout(config, package:)` answers `binding(platform)` (`lib/src/generated/windows/c.g.dart` — under the platform, named after its driver), `glue(platform)`, `assetId(platform)`, `facade(name)` and `bindingImports`. It exists because three things have to agree about one path and none of them can see the others — the driver is handed an output path and an asset id before any content exists, the facade imports each binding relative to itself, and `hook/build.dart` declares the asset the binding's `@DefaultAsset` names. A binding whose asset id nothing declares fails at the first call with nothing to point at, so the three are derived from each other rather than joined three times. Paths are POSIX and relative to `bindsmith.yaml`, which is both a correct import string and a usable path for `dart:io` on Windows, so nothing converts. The loader gained one rule while this was written: generated Dart must live under `lib/`, because a file elsewhere has no `package:` URI and therefore no asset id — reported with its line and column, and stated in the schema so an editor says it too. `Platform.values` orders everything, so reordering the config file cannot change a generated file (rule 6).
- **P5-5** `emitBuildHook(layout)`: one `hook/build.dart` for every platform that set `build:`, since a package may only have one and it runs once per target — so the file is one `if (input.config.code.targetOS == OS.windows)` guard per platform, each declaring that platform's own asset. `native_toolchain_c` compiles the listed sources (`CBuilder.library(name:, assetName:, sources:).run(input:, output:)`), which is the `package_ffi` template's shape; `native_toolchain_cmake` runs an existing `CMakeLists.txt`, installs into the hook's own output directory and picks the library up with `findAndAddCodeAssets`, because CMake names the built file itself. Both emitted hooks are committed under `fixtures/tool/build_hook/` — outside `lib/`, where a file may not import a dev dependency, and not at `hook/build.dart`, where they would run during every fixture build — so `dart analyze --fatal-infos fixtures` type-checks them against the real `hooks`, `code_assets` and `native_toolchain_*` APIs. That is the check that catches an upstream rename; a golden would only notice our own edits. A `build:` that cannot be carried out is refused rather than written: a platform with no native build, `native_toolchain_c` with no sources, `native_toolchain_cmake` with more than one directory, and a path carrying a quote or a `$` that would not survive being written into a Dart literal.
- **P1-4** CLI (`lib/src/cli/runner.dart`, one file; `bin/bindsmith.dart` only supplies the real streams). `runBindsmith(args, out:, err:, workingDirectory:)` returns the exit code instead of calling `exit` and writes through injected sinks, so all thirteen cases run in-process against a throwaway project directory — no `dart run` per case, no `Directory.current` to put back. Exit codes are `sysexits(3)`: 64 bad arguments, 65 a `bindsmith.yaml` that was read and cannot be used, 66 a file that is not there, 70 generation itself. That split is the point of having codes at all — a script can tell "fix your config" from "the generator broke". `init` writes the config **and** `bindsmith.schema.json` beside it with a `# yaml-language-server: $schema=` header, so an editor completes the file it just created; the test loads the template through `loadBindsmithConfig` rather than comparing text, because what makes a template right is that it is a working starting state. `generate` is the whole pipeline: `Layout` from the config and the package name in the neighbouring `pubspec.yaml`, each platform's driver into `layout.binding(platform)`, then `includePass`, `nullabilityPass`, `cFacadePass` and `fixupsPass`, then `emitFacade` at `layout.facade(name)` and `emitBuildHook` at `hook/build.dart`, printing every path it wrote. The `include:` lists become the driver's pull list through a new `SymbolPattern.touchesName`, which keeps `Type` for a `Type.member` pattern — at generation time there is a name and no IR yet, so a pattern that dropped the type would leave the member it names ungenerated. Dispatch covers `c` and `objc`; every other driver raises an error naming the platform and the driver and pointing at `--platform`, because each still needs something the configuration cannot say or resolve (a Swift module name, a `.d.ts` from npm, a Maven classpath through `package:jni`, a `.winmd` from NuGet) and silently generating nothing is rule 3. `dump` runs the same load and prints `irToJson`; `schema` prints the schema alone. One test runs `generate` twice and compares the bytes (rule 6).
- **P1-5** `doctor` (`lib/src/cli/doctor.dart`, `bindsmith doctor [--json]`). Every check has the same shape — find a program or a file, read a version out of it — so the only impure step is one `Probe` typedef the tests hand in, and everything else is data: which tool a driver needs, where libclang hides per operating system, which JDK versions jnigen accepts. Same split as `Pom.parse` against the fetch, and it is what lets the whole matrix be tested on any host: a fake probe reports macOS with no Xcode, Linux with a JDK 11, Windows with no Build Tools, and the expectations are on the report rather than on the machine running them. Two decisions carry the command. Only the toolchains the *configured* platforms need are required — a `bindsmith.yaml` with one `linux: {driver: c}` platform does not fail because the box has no Xcode — and with no configuration at all (a fresh machine, before `init`) everything the host could have is checked and nothing is required, so `doctor` is useful before there is anything to be missing for. And a tool the host cannot have is never reported: asking a Linux box for Xcode is a problem nobody can fix. Every failure carries the command that fixes it (`sudo apt-get install libclang-dev`, `xcode-select -s`, `mise install`), because an error that does not say what to do is rule 8's other half. libclang is found the way ffigen finds it — a library, not a program, so a fixed list of directories per OS rather than a `PATH` lookup — and the Visual Studio Build Tools the documented way, through `vswhere.exe` at its fixed `Program Files (x86)` location. Exit is 0 or 1 (`exitChanged`, the `diff(1)` convention already used by `--check`), so CI can gate on it; `--json` prints the same report for a script.
- **P1-5** `doctor` (`lib/src/cli/doctor.dart`, wired into the runner as one more command). Every check has the same shape — find a program or a file, read a version out of it — so the only impure step is an injected `Probe`, and each case in `test/cli/doctor_test.dart` decides what the machine has rather than asking the machine it runs on. What is left is data: which tool a driver needs, where libclang hides per operating system, which versions the generator that consumes it accepts (JDK 17–21 for jnigen, node 20+ for the sidecar). Three things there are load-bearing. Only a toolchain the *configured* platforms need is required, and only one the host could actually have — asking a Linux box for Xcode reports a problem nobody can fix — so one `bindsmith.yaml` produces a different required set on each machine, and `winmd` requires nothing beyond Dart because `package:winmd` is a pure-Dart reader. libclang is looked for in ffigen 22's own locations, in ffigen's own order, ending at `clang -print-file-name=` (`src/strings.dart`, `src/config_provider/spec_utils.dart`): a `doctor` that searched anywhere else could answer yes where ffigen answers no, which is worse than not checking at all. And MSVC is found through `vswhere.exe` at the fixed path every installer since VS 2017 writes it to, not by looking for `cl` on `PATH` — outside a Developer Command Prompt there is nothing on `PATH` to find, and `VCToolsInstallDir` is the cheaper answer inside one. Without a configuration — a fresh machine, before `init` — everything the host supports is checked and nothing is required, which is what plan §10's "zero to first generation with copy-paste commands" asks for. Exit 1 while a required toolchain is missing; `--json` prints the same report for a script, which is what the issue template asks contributors to paste.

### Phase 2 — Apple: Objective-C and Swift drivers (2 weeks, macOS runner) — C4

- **P2-1** ObjC driver (`lib/src/drivers/c/objc_driver.dart`). Same upstream generator as P1-2, so the two share `ffigen_adapter.dart`: the C pull-list recorder and the read-back of ffigen's spelling (`Dart<name>` twin typedefs, `@ffi.Native<T>`, doc comments). `ObjcDriver.load` adds `objectiveC: ObjectiveC()` — ffigen supplies `-x objective-c` and the `xcrun --show-sdk-path` sysroot itself — plus a second visitor that applies the pull list to interfaces, protocols and categories and records each selector, which the generated Dart does not spell out. `objcToIr` reads interfaces as `TypeDecl(klass)` (representation `objc.ObjCObject`), protocols as `TypeDecl(interface)` (representation `objc.ObjCProtocol`) with a marker naming `X$Builder.implement`, and merges each category's `extension` into the interface it extends. It then runs `cToIr` over the same file, because an Objective-C header still declares enums, typedefs and functions. Recorded rather than silently lost: a block parameter sets `Async.callback` and a marker naming that block's `listener`/`blocking`/`fromFunction` constructors (the `Future` wrapper itself is facade work, P6-4b); ffigen drops an `NSError **` argument and throws instead, which becomes a verify marker; an `@optional` protocol method carries the marker that it throws when unimplemented. Members ffigen invented (`isA`, `conformsTo`, the pointer constructors) have no selector and stay out of the IR. Fixture `fixtures/objc/counter`; generated binding and `.m` glue committed under `fixtures/lib/generated/counter/`.
- **P2-2** Swift driver (`lib/src/drivers/swift/swift_driver.dart`). Dart reaches Swift through Objective-C, so `SwiftGenerator` is a three-step pipeline: swift2objc writes an `@objc` wrapper class for the Swift API, `swiftc -emit-objc-header-path` emits the Objective-C header for it, and ffigen binds that header. The last step is P2-1's territory, so `swiftToIr` is `objcToIr` plus the bookkeeping only this pipeline can do, and `SwiftDriver.load` returns the three files an app has to ship: the Dart binding, the `.m` glue and the generated `.g.swift` wrapper. Inclusion is driven entirely by visitors, because swiftgen passes no `Input.include` to ffigen: an interface or protocol is bound when its name, or its name minus the `Wrapper` suffix swift2objc adds, was offered to `SwiftGenerator.include`. Plain C declarations are never bound by name — the generated header imports Foundation, so a name-based pull list would bind the SDK — while the types a bound signature actually refers to still arrive transitively. Two disjoint kinds of loss are recorded rather than dropped: a declaration swift2objc could not parse never reaches the wrapper and surfaces only as a `SEVERE` record on the logger, so the driver keeps that logger and turns each record into a `Marker.dropped`; a declaration it did accept but that no longer appears in the binding is found by diffing what `include` was offered against what came back, which needs no diagnostics at all. The diff is selector-aware, since a Swift argument label joins the selector (`greet(name:)` → `-greetWithName:` → `greetWithName`). Confirmed limitations of swift2objc 0.3, both exercised by the fixture: a generic type produces an `@objc` wrapper that does not compile (keep it out of the pull list), and a method with an array parameter is dropped with only a log record. Fixture `fixtures/swift/greeter`; binding, glue and wrapper committed under `fixtures/lib/generated/greeter_swift/`. Phase 7 (P7-1) turns the dropped markers into wrapper stubs.
- **P2-4** Fixtures now have implementations, not just headers: `fixtures/objc/counter/counter.m` and the Swift sources build into real libraries that the committed bindings are called against, by `fixtures/bin/counter_objc.dart` and `fixtures/bin/greeter_swift.dart`, each spawned from its driver test and skipped off macOS. This is what `dart analyze` cannot reach — every Objective-C failure mode is a runtime one: a selector that does not exist, a protocol that is only implemented once the callee dispatches to it, a block invoked on the wrong isolate, an `NSError**` that the Dart signature says nothing about. Swift adds three more, because the binding is three translations deep: the mangled class name (`_TtC10GreeterKit14GreeterWrapper`) only resolves if the module really is `GreeterKit`, a Swift struct only arrives as the wrapper class swift2objc writes around it, and an `async` method reaches Dart as a completion handler that Swift invokes from its own executor thread, so it needs `ObjCBlock_….listener` — an ordinary block crashes there. The Swift build is two `swiftc` passes around one `clang`, because each half needs the other's output: `swiftc` emits the Objective-C header the generated glue imports, and the glue's object file then links back into the same module, so one dylib carries both. Building the fixture also compiles `GreeterKit.bridge.g.swift`, which is the only check that the P7-1 bridge emitter writes Swift that a compiler accepts. Two bugs came out of doing this: `implement` for a protocol is a static on the `$Builder` class rather than the `$Methods` extension, and — the one that mattered — ffigen wrote the glue's `#import` as a relative walk from the generated file to an absolute entry point, so a committed file carried `/Users/…` and built nowhere else (rule 6). The driver now rewrites it to the header's own basename, found through the include path a podspec or a build hook sets, the same way the Swift glue already imported `<Module>-Swift.h`.

### Phase 3 — Android: JVM driver, Maven resolution, lockfile (2 weeks) — C4

- **P3-2** `deps/maven.dart`: `MavenResolver.resolve(['group:artifact:version'])` → `List<MavenArtifact>` (coordinate, extension, file on disk, sha256). Reusing jnigen's Maven support was the plan and is not possible: `GradleTools` writes a stub Gradle project and runs `gradlew`, which is driving a tool through its console (rule 1) and pins nothing, so this is an own implementation. `package:http` was not needed either — `dart:io`'s `HttpClient` does it, and `MavenFetch` is injectable so every resolution test runs against an in-memory repository. `Pom.parse` is a pure function with its own unit tests, the way passes are; the resolver folds in `<parent>`, `<properties>`, `<dependencyManagement>` and BOMs imported with `<scope>import</scope>`, filters `<optional>` and non-transitive scopes (a *direct* `provided` is kept, the way a Maven compile classpath keeps it), applies `<exclusions>` down the subtree, and lets the nearest definition of a module win. New dependencies: `xml` (POMs are XML), `archive` (an `.aar` is a zip and its `classes.jar` is the classpath entry), `crypto` (sha256). One repository is not enough, and only a real artifact showed it: `androidx.annotation:annotation-experimental:1.4.1` is served by Google's Maven and its `kotlin-stdlib` only by Central, so `repositories` is a list searched in order and an unresolvable coordinate reports every repository tried. Version ranges, `LATEST`/`RELEASE` and `-SNAPSHOT` are refused by name rather than resolved, because each makes the same coordinate mean different bytes on a different day and there is nothing honest to write in the lock. The cache mirrors the repository layout, so it *is* a Maven repository and a second run needs no network — which is most of P3-3.
- **P3-3** `bindsmith.lock` and `bindsmith resolve` (`lib/src/deps/lockfile.dart`, the command in `runner.dart`). The lock is YAML, `version: 1` and a section per kind of dependency, each a list of `coordinate` / `extension` / `sha256` sorted by coordinate so that reordering the configuration cannot rewrite the file (rule 6). Three decisions about what it does *not* record. It does not name the repository that served the bytes: once the digest matches, where they came from does not change what you compiled against, and recording it would churn the lock every time a mirror is added. It does not say which platform asked — a coordinate names the same bytes whoever wanted it, and a dependency two platforms share should be downloaded and written once. And a kind whose resolver has not landed is refused by name (`lockKinds`) rather than carried through, so a typo cannot look like a working lock; `npm` and `nuget` join the set with P4-4 and P5-2. `parseLockfile` reports every problem with its line and column through `source_span`, the way the config loader does, because the lock is read by every offline build and a file it half-understands is worse than one it rejects. The digest is the one field YAML can get wrong by itself: one made of nothing but decimal digits resolves to a number, an integer or a float once it outgrows one, and so does every digest in a lock written before bindsmith started quoting them. A non-string scalar under `sha256` is therefore read back from the source text rather than refused, and then checked against `^[0-9a-f]{64}$` — the check is what makes reading raw text safe, and it also catches a truncated or uppercased digest, which would otherwise never equal a freshly computed one and would be reported as changed bytes on every run. bindsmith still writes the digest quoted, since a build script reading the lock with another YAML library falls into the same trap with no such fallback. `resolve` merges each platform's `deps.maven` through `MavenResolver` into `.dart_tool/bindsmith/maven`, prints `+`/`-` per coordinate and writes the lock; `--check` re-serialises the parsed lock and compares, so whitespace someone tidied is not a failure while a missing artifact is, and it exits 1 as `generate --check` does. A coordinate whose bytes disagree with the lock is a hard error naming it, never a rewrite: a released artifact does not change, so either the lock was edited or something is serving other bytes under that name (rule 3). `--offline` installs a `MavenFetch` that throws, which is exactly the question being asked — the download cache is itself a Maven repository, so a resolve that can be answered from it never calls fetch at all. Testing this end to end needed no injection and no network, because `file:` repository URLs are now accepted alongside `https:` (Gradle spells the same thing `maven { url = uri("file:///…") }`, and a vendored or mirrored repository on a shared drive is a real thing to want); `mavenFetch` reads them, and the CLI test publishes two artifacts into a temporary directory, resolves, deletes the repository, and resolves again `--offline`. Plain `http:` stays refused: an artifact fetched over it is one whoever is between you and the mirror chose, and it would then be pinned as if it were yours.
- **P3-1** JVM driver (`lib/src/drivers/jvm/jvm_driver.dart`). `JvmDriver.load` runs `JniGenerator(input: Input(classes:, sourcePath:, classPath:), output: Output(dart: DartOutput(structure: singleFile)), visitors: [...])` and then reads the emitted Dart back with `package:analyzer` — jnigen's own AST carries names and inclusion but no resolved Dart types, the same gap as ffigen (P1-2), so the driver uses the same read-back pattern. The authoritative Java link is the `/// from: \`<declaration>\`` doc line jnigen writes above every member; `jvmToIr` parses it for the binary name, static-ness, return type and parameter types (depth-aware split, so `Map<String, Integer>` survives). Classes map to `TypeKind.klass`, `interface` (body has `implementIn`) or `enumeration` (implements a local type documented `java.lang.Enum`); jnigen's stub classes become dropped markers, interfaces get a `verify` marker naming `X.implement`. A pull list is honoured through a `Visitor` that sets `c.isIncluded`. Kotlin metadata (nullability, `suspend → Future`) and the `Flow`/default-argument markers landed with the Kotlin fixture in P3-5.
- **P3-5** Kotlin through the JVM driver, and JVM tests that actually run. jnigen 1.0 reads Kotlin metadata and writes a member found there in Kotlin's own spelling on the `from:` line (`public suspend fun greetSlowly(name: kotlin.String): kotlin.String`, `vararg`, `operator`, a trailing `where` clause), while constructors, property accessors and fields keep the Java form and a compiler-made member carries a `synthetic` prefix; `jvmToIr` parses both. Parameter names come from the Kotlin line, because the Dart binding uses the bytecode names (`string`, `i`) — except where the Kotlin name is a Dart reserved word, or the arity differs (an extension receiver). `suspend` becomes `Async.future` over the awaited type, and a `Flow` return carries a verify marker pointing at `emitKotlinBridge`. Default arguments needed class files: jnigen's summarizer drops the synthetic `static f$default(…, int mask, Object)` methods, so nothing in the binding says a method has defaults — and the P7-2 bridge keys its shorter overload on exactly that sibling. `JvmDriver.load` therefore reads the bound classes from the class path itself (directories and jars, through the `archive` dependency already there for `.aar`s): `classFileMethods` is a small JVMS §4 reader, constant pool through method table, that throws `FormatException` on a bad magic or a truncated file, and every `ACC_STATIC | ACC_SYNTHETIC` method named `…$default` becomes a dropped member saying what was lost and that `@JvmOverloads` binds each arity instead. Synthetic constructors do survive jnigen (as `new$N`) and are dropped with a reason that tells the two kinds apart: the default-argument carrier (`…, int, DefaultConstructorMarker`) and the path to a private constructor (a companion's), which nothing should call. KDoc does not reach Dart: jnigen summarizes compiled classes, and they carry none.

  Running jnigen at all took two more things. It calls `exit(1)` when `package:jni` does not resolve, which inside `dart test` ends the runner rather than failing a test, so `load` first repeats jnigen's own lookup (`findPackageConfig(Directory.current)`, then `Isolate.packageConfig`; new dependency `package_config`) and throws a `StateError` saying what to add. And jni declares a Flutter SDK constraint, so this workspace cannot depend on it: `JniProject` (`test/jvm_toolchain.dart`) writes a throwaway package that depends on bindsmith by path and on jni, resolves it with `flutter pub get`, and runs jnigen as `dart --packages=<its package config>` from the repository root, so the summarizer jar in `.dart_tool/jnigen/` is still shared and jni's lookup falls back to that package config. `dart run jni:setup --build-path` builds `libdartjni` once into `.dart_tool/bindsmith/jni-<version>/` beside `jni.jar`, and `test/drivers/kotlin_test.dart` ends by calling the generated binding from a separate Dart process on a desktop JVM through `Jni.spawn(dylibDir:, classPath: [jni.jar, classes, kotlin-stdlib, kotlinx-coroutines-core])`: overloads, a nullable return, a Dart-implemented listener, a sealed result, the companion, and a `suspend` function that really suspends (`delay(1)`, so it resumes on another thread). The same suite feeds the driver's IR to `emitKotlinBridge` and compiles the result with `kotlinc`, which is what the hand-written IR of the bridge tests could not prove; the emitter learned to write `String` for `kotlin.String` and `List` for `kotlin.collections.List`, which is how that IR spells them. Binding and IR are goldens under `test/drivers/goldens/ktgreeter_jvm.*`. `mise.toml` gained Flutter 3.47.1 and CMake 3.31.12 (libdartjni is a CMake build); without Flutter or a JDK both JVM suites read their committed goldens and skip only what needs a process.
- **P3-4** Android glue (`lib/src/emit/android_glue.dart`). `emitAndroidGlue(layout, ir)` writes two files beside the package's `android/build.gradle` rather than into it, because that file belongs to the author: `android/bindsmith.gradle`, applied once with `apply from:`, and `android/bindsmith-rules.pro`. The rules are the point. jnigen looks a class up by name the first time Dart calls it, which R8 cannot see, so a release build strips or renames every bound class the Java side does not use itself and fails with `ClassNotFoundException` in release only (jnigen's README FAQ). So there is one `-keep class <binary name> { *; }` per bound class — none for a class jnigen only stubbed — sorted (rule 6), plus `-keep class kotlin.coroutines.** { *; }` when the binding has a `suspend`, the rule jnigen's own `kotlin_plugin` example ships. They reach apps as `consumerProguardFiles` of the package's Android library, the mechanism `package:jni` uses for its own classes, so an app depending on the package keeps them without doing anything. They are taken from the IR's bound classes, not from the pull list, which holds patterns rather than what jnigen actually bound. The script also declares the Maven dependencies the binding was generated against, with the configured repositories in order (Maven Central when none are configured, as the resolver does); only the direct coordinates, since Gradle resolves the transitive ones itself. `ffiPlugin: true` is not bindsmith's to write — the pubspec is the author's — so the script's header says where it goes, next to the one `apply from:` line. Coordinates and repository URLs go into single-quoted Groovy literals, which interpolate nothing, so only a quote or a backslash is refused. `Layout` owns both paths (`androidGradle`, `androidRules`) and `_emit` adds the two files for an Android platform on the `jvm` driver; that takes effect once the driver is wired to the command line, which still needs a class path of the resolved Maven artifacts plus the SDK's `android.jar`. `doctor` now reports that jar rather than the SDK directory: the newest `platforms/android-N/android.jar` (a minor release such as `android-36.1` counts, an extension SDK does not), and an SDK with no platform installed is a problem whose fix names `sdkmanager`. There is no `compileSdk` key for the plan's "platform jar for the configured compileSdk" to check against, so it checks the newest one installed. Goldens under `test/emit/goldens/android/`.

### Phase 6 — Unified facade, passes, fixups, verify (2 weeks) — C5

- **P6-2** Passes: include/exclude (globs), rename, nullability overrides, async mapping (`suspend`/completion handler/`Promise` → `Future`; `Flow`/`AsyncSequence`/event listeners → `Stream`), threading (`main` → listener blocks / `NativeCallable.listener` / `scheduleMicrotask` notes), availability (`@available`/`@RequiresApi` → dartdoc `@since` + optional runtime guard), doc propagation (HeaderDoc/Javadoc/TSDoc → dartdoc), size budget.
- **P6-2, doc follow-up** (2026-09-11). An audit of what each driver actually carried found the docs in the IR were often not the source's. Each gap was fixed where the text enters, so every emitter gets it for free. ffigen reads plain `//` and `/* */` as well as `///` (`sourceComments`, `CommentStyle.any`); clang itself marks a comment after code as trailing and pins it to that line's declaration, which the geometry fixture's `SHAPE_CIRCLE = 0, // Measured by its radius.` asserts. ffigen documents an undocumented Objective-C declaration with its own selector (`fallbackComment`), so `objcToIr` drops a doc equal to the selector or the class name. That filter is what exposed the Swift gap: swift2objc writes its wrapper without comments, so a kept Swift class had only selectors for docs. `swiftToIr` now fills them from the symbol graph, keying a member by the name ffigen gives it (`greet(name:)` → `greetWithName`). ffigen's `dartDoc` is `final`, so the raw binding cannot be corrected, only the IR. jnigen puts a ``from: `…` `` line and a release note above every member; `_docs` strips both, `_from` reads the raw text, and Javadoc `{@code}`/`{@link}` become Markdown. The sidecar now lists JSDoc tags as written (it stays syntactic). The driver renders `{@link X}` as `[X]` and `@param`/`@returns`/`@example` as prose, and turns `@deprecated`/`@since` into `Availability`, which `js_interop.dart` now writes as `@Deprecated` just as the facade does. The facade writes each enum value's docs. Left open, each now a task in `plan.md`: Kotlin KDoc (P3-7; jnigen reads compiled classes, so it needs a `.kt` reader of our own, and P3-8 for Maven artifacts), the ObjC category doc (P6-9; the binding keeps it, but the IR has no category node), macro and same-name-typedef struct comments ffigen cannot attach (P6-8), parameter docs, which the IR has no field for (P6-7), and Swift docs in the raw binding (P2-5; swift2objc writes its wrapper without them).
- **P6-3** Fixups DSL and ordered application.
- **P6-4** Facade emitter (`lib/src/emit/facade.dart`, `emitFacade`): `<lib>.g.dart` with `export '<lib>_io.g.dart' if (dart.library.js_interop) '<lib>_web.g.dart';`, `<lib>_io.g.dart` dispatching on `bindsmithPlatform` (constant-folded by AOT) to the android/ios/macos/windows/linux bindings, `<lib>_web.g.dart` delegating directly. Symbols matched by Dart name, members by kind + staticness + name; the first configured platform gives the shape, differences become `@BindsmithVerify`, missing symbols follow `unsupported: throw|stub|omit`, everything left out is listed in a trailer comment. Marshalling: jni `toJString`/`toDartString`, objective_c `NSString(x)`/`toDartString`, js_interop primitives + `JSArray`/`JSPromise` conversions + object-literal constructors; anything else passes through with a verify marker. Goldens in `test/emit/goldens/` and on the web fixture.
- **P6-4b** Facade over C. Split in two: `cFacadePass()` (`lib/src/passes/passes.dart`) rewrites the IR's dart:ffi types into the API the facade offers and leaves the dart:ffi spelling in `TypeRef.native`, and `emitFacade` reads that `native` to write the marshalling. `Pointer<Char>` → `String`, allocated with `toNativeUtf8(allocator: _arena)` inside a `using` that wraps the whole call, and read back with `cast<Utf8>().toDartString()` plus a marker saying the library owns the returned bytes. `Pointer<X>` for an opaque `X` → `X`, whose facade object already holds the pointer; a one-argument `void` `*_free`/`_destroy`/`_release`/`_delete`/`_close` taking that handle becomes `X.dispose()` forwarding to the facade function, which stays callable (two candidates and neither is chosen). `Pointer<X>` for a struct → `X`, copied into the arena through `Pointer.ref`; a struct by value needs no marshalling at all, because dart:ffi passes it. A C enum crosses by constant name (`linux.Shape.values.byName(shape.name)`), because ffigen types an enum parameter with its own Dart enum; the facade enum carries the C values and a `fromValue`. A C typedef is dropped and replaced by what it aliases, so no signature names a declaration the facade does not emit; a pointer whose dart:ffi spelling names a binding-library type (a callback) degrades to `ffi.Pointer<ffi.Void>` with a marker and is cast back at the boundary. `dart:ffi` and `package:ffi` are imported only when the body uses them. Fixture `fixtures/lib/generated/geometry/geometry_facade*.g.dart`; `test/emit/facade_c_test.dart` builds `fixtures/c/geometry/geometry.c` into a shared library and calls the facade through `fixtures/bin/geometry_facade.dart`, which is the only check that catches a wrong arena or a wrong string encoding. Constructing a struct from Dart is P6-4c.
- **P6-4c** Struct construction. The premise this row was written on turned out to be wrong: nothing has to be allocated and nothing is owned. `ffi.Struct.create<T>()` lays a struct out on the Dart heap, so `Point(x: 1, y: 2)` is a plain Dart object collected like any other, and the `dispose` this row asked for would have been a lie — the marker says exactly that, right next to the opaque handle on the same page that really does need one. `cFacadePass` synthesizes the constructor (one named parameter per field, in declaration order) and a setter per field; the emitter turns the `laidOutAs` marker into `Point._((ffi.Struct.create<linux.Point>()..x = x..y = y))`, the same pass/emitter contract as `disposedBy`. A nested struct is copied in by assignment and read back as a view into the container's memory, which is C's behaviour and carries its own marker. A struct with a pointer field gets neither a constructor nor a setter for that field: the facade would marshal the pointer through an arena freed before the struct is used, so it would hand back something already dangling. `fixtures/bin/geometry_facade.dart` builds, mutates and nests structs against the real library, and that run is what exposed P6-4d.
- **P6-4d** Struct out-parameters. `void geometry_scale(Point *p, double f)` crosses as an arena copy, so before this the library scaled the copy and the caller's `Point` never changed. dart:ffi copies a struct *into* a pointer (`ptr.ref = value`) but has no way to copy one out, so the write-back is field by field, from the field list the IR already carries. The emitter needed one new thing to express it: an argument expression cannot name the pointer it just allocated, so `_toC` hoists `final _p0 = ...` into `_Ctx.pending` and `_withArena` drains it, turning `using((_arena) => call)` into a block that declares the locals, runs the call, writes back, and returns the result — or just runs the call, when the function is `void` and there is no result to hold but still work to do afterwards. Every struct-by-pointer argument is written back, because ffigen does not carry `const` into the Dart signature and so nothing here can tell an in-parameter from an out-parameter; the cost is a few field copies on a call that did not need them. A nullable struct argument keeps the old one-way copy and its marker: `null` has nothing to write back into. `fixtures/bin/geometry_facade.dart` asserts the round trip against the real library.
- **P6-5** `verify` (`lib/src/verify/verify.dart`, `_Verify` in the CLI). It reads the generated Dart that is *committed* rather than generating again, and that is the whole distinction between it and `generate --check`: `--check` says whether the output is current, `verify` says whether it is finished. Reading the file is also the only reading that matches how a marker is acknowledged — a `fixups: … ack: true` entry drops the marker before any emitter sees it and a human may simply delete the annotation, so what is left in the file is the whole answer. The consequence is the useful one: no libclang, no JDK, no network, so this is the gate that can run on every push. Everything it decides is a pure function of source text (`findMarkers`, `publicApi`, `facadeDrift`, `countLines`), the way a pass is a pure function of IR; the command only finds the files. `publicApi` parses a facade group and keys every public declaration to its own source with the body left off, so a difference reads as the two lines a caller would see; initializers are left off with it, because a `const` whose value differs per platform is the point of the facade and not a defect. `facadeFileNames` moved into `facade.dart` and `emitFacade` now keys its own output off it, so verify cannot develop its own idea of what the group files are called. A file that does not parse is one finding rather than an exception — that is exactly the state a generated file is in after a bad hand-edit, which is what verify exists to catch. Only markers answer to configuration (`verify: markers: warn` downgrades them); drift between the io and web facades and the `size_budget` are not opinions a configuration can hold, and always fail. Two deviations from the row as written: the exit code is 1, not the plan's early "exit 5", because the CLI settled on `sysexits(3)` and 1 is what `diff`, `generate --check`, `resolve --check` and `doctor` already mean by "the answer is no"; and `verify.compile`, the compile matrix, is not run here — it needs the toolchains this command deliberately does not, and belongs with the end-to-end matrix. The two committed facade goldens are the fixture for the parity check, since they are a real pair of group files carrying real markers.
- **P6-6** `explain`, `diff`, `watch`, `generate --check`. All four are the same load with a different destination, so the pipeline moved behind one function that takes an output root: the drivers write their binding somewhere by construction, and a command that only reads points them at a directory it deletes. That is what makes `--check` honest — it is the whole run again, into a throwaway directory, compared against what is committed, touching nothing in the tree it is checking, so CI can run it on a clean checkout (rule 6). It also caught the thing worth catching: because the scratch directory has a different absolute path every time, a check that passes proves no generated file embeds where it was generated — the exact bug that had put a `/Users/…` walk into the Objective-C glue in P2-4. `dump` and `explain` became read-only in the same change; before, printing the IR wrote a binding into the project as a side effect. `diff` compares an earlier `dump` against the current sources symbol by symbol, on shape rather than on JSON, because markers and doc comments move constantly while a changed signature is what breaks a caller; it exits 1 when anything differs, the convention of `diff(1)`, and prints `~` with the previous shape under it. `explain` takes an `include:`-shaped pattern and prints, per platform, what the symbol became, where it came from and every marker on it and its members — the command that answers "why is this a `Pointer` / why is this nullable / where did my method go", which is what rule 3's markers exist for. `watch` polls the config and every header it names, keeps running when the configuration is broken (which is most of the time while it is being edited) and stops when the config is deleted; the stamps are taken *before* a run, not after, or a header edited while generation is in flight is absorbed and never rebuilt. Twenty-five cases, four seconds, no subprocess.

### Phase 7 — Slim-binding wrapper generation (2 weeks) — C5

- **P7-1** Swift bridge emitter (`lib/src/emit/swift_bridge.dart`, `emitSwiftBridge`): the `dropped` markers P2-2 records are turned back into a compilable `@objc public final class <Type>Bridge: NSObject` that holds the Swift value (`public var wrapped: <Type>`) and is constructed from the wrapper swift2objc already emitted (`init(_ wrapper: <Type>Wrapper) { wrapped = wrapper.wrappedInstance }`), so the bridge composes with the existing pipeline instead of replacing it. A dropped member is re-declared with an Objective-C-representable signature and forwards to the Swift one: `[X]` → `NSArray` with `as! [X]` on the way in and `as NSArray` on the way out, `[K: V]` → `NSDictionary`, `Set<X>` → `NSSet`, and a Swift type that swift2objc *did* wrap travels as that wrapper, unwrapped with `.wrappedInstance` and re-wrapped on return — which is what makes a struct crossable without a JSON encoding. `async` becomes `completion: @escaping (T) -> Void` driven by a `Task`, but only for members swift2objc lost: it already lowers a parsable `async` method to a `completionHandler:` selector itself, so the bridge does not duplicate that work. What genuinely cannot cross is refused rather than mis-emitted — constructors, `AsyncSequence`, tuples, function types, a Swift-only type with no wrapper, and anything generic (`Box<T>` is unrepresentable in Objective-C at all) — each refusal written as a `// Not bridged: …` comment in the generated Swift and left as a `dropped` marker for `bindsmith verify`. The bridge is re-fed through `SwiftDriver` with `objcCompatibleSources`/`objcCompatibleTypes`, which uses swiftgen's `ObjCCompatibleSwiftFileInput`: those files skip swift2objc and go straight to `swiftc`, so the bridge is compiled next to the wrapper and bound by the same ffigen run. Signatures for dropped declarations come from the Swift symbol graph (`lib/src/drivers/swift/symbolgraph.dart`), the only place they survive, and the generated Objective-C glue has its temp-directory `#import` rewritten to the shipped `<Module>-Swift.h` so output stays byte-identical between runs. Round trip proven end to end in `test/drivers/swift_test.dart`: `Greeter.greetAll(names:at:)` is dropped by swift2objc, re-emitted as `GreeterBridge`, compiled, and arrives in Dart as `greetAllWithNames`. Golden `fixtures/lib/generated/greeter_swift/GreeterKit.bridge.g.swift`; 12 emitter unit tests in `test/emit/swift_bridge_test.dart`.
- **P7-2** Kotlin bridge emitter (`lib/src/emit/kotlin_bridge.dart`, `emitKotlinBridge`). jnigen carries more Kotlin than the Swift pipeline carries Swift — nullability and `suspend` both come out of the class metadata, and `KotlinProcessor` turns a `suspend` function into a `Future` on its own — so unlike P7-1 there are no `dropped` markers to work from. What jnigen binds instead is *unusable*, and the emitter is driven by three shapes it can recognise in the IR. A default argument: Kotlin compiles it to a synthetic `greet$default(receiver, …, int mask, Object marker)` alongside the full-arity method, so the presence of that sibling is the signal, and the bridge emits an overload that forwards with **named arguments** (`wrapped.greet(name = name)`), which is what makes the omission legal whatever position the default sits in. Which parameters are optional is in neither the bytecode nor jnigen's Kotlin metadata (`KotlinValueParameter` carries name, type and vararg element only), so `Param.optional` is honoured when a pass has set it and the last parameter is assumed optional otherwise; when that assumption is wrong the generated file does not compile, which is the loud failure rule 3 asks for, and the emitted KDoc names `@JvmOverloads` as the fix. A `Flow<T>` return: recognised by `TypeRef.native` starting `kotlinx.coroutines.flow.Flow<`, and re-exposed as a nested `interface <Member>Sink { onValue; onError; onDone }` plus a method that collects into it on a `CoroutineScope(Dispatchers.Default)` and returns an `AutoCloseable` that cancels the job — the listener-plus-handle pair the facade turns back into a `Stream`. A sealed base: recognised as a type other types name in `supertypes`, and given a `kind` property (`wrapped.javaClass.simpleName`, no reflection) plus one checked `as<Sub>()` per subclass, because JNI can only reinterpret a reference. Everything else is left alone: an enum, a `suspend` function and a type with none of the three shapes get no bridge at all. Comments are KDoc wrapped at 80 columns, not `///`, so jnigen reads them out of the metadata and hands them to Dart. A generic type and a Java type with no Kotlin spelling (a type variable, a wildcard) are refused with the reason as a comment and stay reported by `bindsmith verify`. Fixture `fixtures/jvm/ktgreeter` (default argument, `Flow`, sealed `Reply`, plus a `suspend` method that must stay untouched); golden `KtGreeter.bridge.g.kt` next to it; 12 tests in `test/emit/kotlin_bridge_test.dart`, the last of which compiles the emitted bridge together with the fixture using `kotlinc` (mise now pins Kotlin 2.4.20; the coroutines jar ships inside the distribution). Two deliberate deviations from the original row. The round trip back through `JvmDriver` is not executed, because jnigen resolves `package:jni` and this pure-Dart workspace cannot provide it — the same reason the JVM end-to-end tests skip — so the IR in the tests is hand-written from the `javap` output of the compiled fixture and the compile check proves the other half. And no Gradle module snippet is generated: the bridge is one source file that the plugin's existing Android module already compiles, and build glue belongs with the rest of it in P5-5 rather than duplicated here.
- **P7-3** C++ shim emitter (`lib/src/emit/cpp_shim.dart`, `emitCppShim`) writing `shim.g.h` and `shim.g.cc` from the IR, so the shim and the Dart binding cannot drift. bindsmith does not parse C++ and will not (§1), so the input is a description rather than a driver: a `TypeDecl` whose `id` is the qualified C++ name (`greeter::Greeter`) and whose `TypeRef.native` holds the C++ spelling. Each class becomes an opaque handle (`typedef struct greeter_Greeter greeter_Greeter;`) with a factory per constructor, a `_delete`, and one function per member, taking the handle as `self` unless the member is static. Three things the boundary has to get right are in the generated source rather than left to the caller. **Exceptions**: a C++ exception unwinding through `extern "C"` is undefined behaviour, so every body runs inside a `bindsmith_guard` template that catches `std::exception` and `...`, records the message in a `thread_local`, and returns a value-initialised result; the caller reads `<prefix>_last_error()`, which is `NULL` after a call that worked. **Ownership**: an `std::string` result is copied onto the C heap with `malloc` and released by `<prefix>_free_string`, and a class result is heap-copied and released by that class's `_delete`, so nothing ever returns a pointer into a temporary. **Null**: a `const char*` argument is never handed to `std::string` unchecked, because `std::string(nullptr)` is undefined. A reference parameter crosses as a pointer and is dereferenced on the C++ side; C++ overloads, which cannot share a C name, are disambiguated with a numeric suffix. `std::vector`, a template, and any type not named in the IR are refused with the reason as a comment in the header and keep their markers. Fixture `fixtures/cpp/greeter` (constructor, `std::string` in and out, a throwing method, a void setter, an int getter, a static, and a `std::vector` return that must be refused); goldens `shim.g.h`, `shim.g.cc` and the bound `fixtures/lib/generated/greeter_cpp/shim.g.dart`. 12 tests in `test/emit/cpp_shim_test.dart`, two of which are the real round trip: one compiles the fixture and the shim into a shared library with the system C++ compiler, loads it through `dart:ffi`, and checks that a throwing call returns `NULL` and leaves the message in `last_error` instead of unwinding; the other runs the header through `CDriver` and checks the handle arrives as an opaque struct with its documentation intact. The `native_toolchain_cmake` hook that builds the shim is not part of this: `hook/build.dart` templates are P5-5, which already names this shim as its C++ input.
