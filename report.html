Research · September 8, 2026

bindsmith

How to build a command-line generator of native-API bindings for the six Flutter platforms — Android, iOS, macOS, Windows, Linux and Web — and what already exists for that in Dart, .NET, NativeScript and the Rust world.

Method: 8 research agents → 5 fact-checks → synthesis Claims refuted: 17 Project files: ~/GitHub/bindsmith/research.md · plan.md · AGENTS.md
Verdict

Write it in Dart, as static codegen, as an orchestrator over the official generators. All the bricks for the individual platforms exist and are alive: ffigen 22 (C and Objective-C), swiftgen 0.2 (Swift), jnigen 1.0 (Java/Kotlin), package:win32 built from Win32Metadata, dart-dbus, dart:js_interop. No tool takes one declaration and emits bindings for all six platforms plus a unified Dart facade — the closest, flutter_rust_bridge, does it only for Rust input.

The bindsmith niche: one config → drivers over ffigen/swiftgen/jnigen/winmd/dbus and an own .d.ts driver for Web → one intermediate representation → passes (filters, renames, nullability, async, threading, fixups) → platform bindings, a facade with dispatch, thin native wrappers for what does not bind directly, and a dependency lockfile. The dynamic NativeScript path is rejected: its own runtime, no tree-shaking, ≈3.5× per-call overhead.

Problem

Task and scope

We need a program that takes a description of a native API — C/Objective-C headers, Swift modules, JAR/AAR, TypeScript declarations, .winmd, .gir, D-Bus XML — and generates Dart bindings for every Flutter platform, runs from the command line and is driven by config files. Reference points: Mono/Xamarin/.NET MAUI, NativeScript, plus uniffi, flutter_rust_bridge and Gluecodium.

Two interop directions must be kept apart. First, native → Dart: Dart calls an existing native API directly (ffigen, swiftgen, jnigen, js_interop). Second, Dart ↔ native over channels: we define a message interface and generate both sides (pigeon). The task is the first one; pigeon stays the escape hatch where a direct call is impossible.

Who uses what

  • Flutter-team plugins (webview_flutter, camera, video_player, in_app_purchase, local_auth) — pigeon; path_provider, url_launcher, shared_preferences — hand-written channels.
  • Dart team: cupertino_http — ffigen ObjC; ok_http — jnigen; sqlite3 — ffigen C.
  • HERE SDK — Gluecodium with an official Dart target. Sentry and Nutrient are moving to FFI/JNI bindings instead of channels not re-verified.
  • No vendor generates Flutter wrappers from an SDK automatically.

What hurts plugin authors

  • Web is always a separate implementation — pigeon does not cover it.
  • jnigen needs a compiled classpath: "build Android first".
  • Swift-only SDKs without @objc are invisible to ffigen; Swift structs and generics do not bridge.
  • Kotlin coroutines, default parameters and companion objects need a facade.
  • Memory and threads: JNI global refs, main-thread UIKit APIs, callbacks the GC collects.
  • Every tool has its own config; YAML → Dart-script migration in 2026.
Landscape

Analogs in other ecosystems

What to take from them: decisions, not code.

Mono · Xamarin · .NET MAUI

Hand-written IDL, generator, fixups, slim binding

  • bgen (iOS/macOS): ApiDefinition.cs with [BaseType], [Export], [NullAllowed], [Wrap]; every Apple SDK is bound this way, by hand. The RFC for a Roslyn generator has been open since 2024 with no work.
  • Objective Sharpie: dotnet global tool Sharpie.Bind.Tool, macOS only, libclang. The [Verify] attribute deliberately breaks compilation until the developer reviews the spot. The best UX for forced review.
  • .NET for Android: class-parse (bytecode + Kotlin metadata) → api.xml → generator; fixups in Metadata.xml on XPath (remove-node, attr, add-node); <AndroidMavenLibrary> in .NET 9 pulls Maven and verifies dependencies.
  • Native Library Interop: the official advice is not to bind the SDK as a whole but to write a thin Swift/Kotlin wrapper and bind that (template in CommunityToolkit/Maui.NativeLibraryInterop).
  • CsWin32: pull model — NativeMethods.txt lists the APIs you need, the source generator takes them from .winmd. CppSharp 1.2, ClangSharp 21.1.8 — C/C++ through libclang with a passes pipeline.
NativeScript

The dynamic pole

  • Metadata for the whole SDK is generated at build time: iOS — C++/libclang generator → binary metadata-<arch>.bin; Android — ASM/BCEL → tree streams.
  • The runtime (V8 on iOS since 7.0, 2020) dispatches through libffi/objc_msgSend and JNI reflection. 100% coverage without per-library codegen.
  • Filtering — native-api-usage.json (whitelist/blacklist); IDE types — ns typings ios|android; type packages of 15 and 48 MB.
  • Price: runtime and metadata in the binary, no tree-shaking, ≈3.5× per-call overhead by NativeScript's own benchmark. Closed for Flutter with AOT on iOS. We take the API-usage whitelist idea.
  • Relatives: dart_native (Alibaba) — abandoned since December 2022; PyObjC, Pyjnius, JNA, koffi.
Rust and IDL

One model and templates

  • uniffi-rs 0.32: Rust → Kotlin/Swift/Python/Ruby; third-party Go, C#, React Native and Dart (Uniffi-Dart 0.2.1, active). ComponentInterface + Askama templates + compatibility checksums.
  • flutter_rust_bridge 2.13: the only mature "one declaration → 6 platforms", but Rust input only; flutter_rust_bridge.yaml, cargokit or native assets.
  • Gluecodium 14.1 (HERE): LIME IDL → C++, Java, Kotlin, Swift, Dart. Djinni is dead (2023 release), SWIG and wit-bindgen have no Dart.
  • objc2 header-translator: translation-config.toml per framework — skipped, per-OS availability, safety flags. The model for declarative fixups.
  • gtk-rs gir: Gir.toml, two layers sys and safe. windows-bindgen 0.100: --filter as a pull model from winmd.
Kotlin · Swift · Java · JS

Mapping lessons

  • Kotlin cinterop .def; Swift export experimental; SKIE 0.10 fixes suspend/Flow on the Swift side; karakum — .d.ts → Kotlin through the TypeScript Compiler API.
  • swift-java 0.6: FFM (JDK 25+) and JNI (Android) modes. jextract: dump-then-curate — --dump-includes, edit, --config.
  • React Native codegen from TS specs; Nitro/nitrogen; Expo Modules DSL. Agora Terra: cppast + libclang → AST → TS renderers, YAML config.
  • Common: async differs everywhere (suspend/Flow, Swift async, Promise → Future/Stream); nullability from annotations; generics erased; docs lost almost everywhere; snapshot tests and a compile matrix are standard.

Decision: static codegen. From the dynamic world we take the pull model (a list of the APIs in use) and type generation from metadata.

How it is done

How native-API interop is generated on each platform

One scheme: input → generator and config → commands → runtime → build → pitfalls. Snippets are schematic: class names come from the ffigen 22 and jnigen 1.0 changelogs, exact signatures are in the package API docs.

Android

stablejnigen 1.0.0 · jni 1.0.3
Input
.class, JAR/AAR (including from Maven) or Java sources. Kotlin only compiled; its metadata gives nullability and suspend.
Config
tool/jnigen.dart; YAML remains as legacy.
import 'package:jnigen/jnigen.dart';

void main() => JniGenerator(
      input: Input(
        classes: ['androidx.biometric.BiometricPrompt'],
        // maven dependencies, android_sdk_config(add_gradle_deps), source_path…
      ),
      output: DartOutput(path: Uri.directory('lib/src/android/')),
    ).generate();
Commands
dart run tool/jnigen.dart. For a plugin with an Android example jnigen runs Gradle itself to obtain the classpath.
Runtime
package:jni: JObject, JString, JList/JMap, Jni.spawn() for a desktop JVM, interfaces implemented from Dart via implement(), global refs released with .release().
Build
ffiPlugin: true, Gradle dependencies, R8/ProGuard keep rules for classes called from Dart; JDK 17–21.
Pitfalls
  • Numbered overload suffixes change between generator versions.
  • Coroutines, default parameters and companion objects need a Kotlin facade.
  • A callback object must be kept in a Dart reference or the GC collects it.

iOS and macOS

ObjC stableSwift experimentalffigen 22 · objective_c 9.6 · swiftgen 0.2
Input
Objective-C: framework headers (system, from an xcframework or a pod). Swift: a module; swiftgen itself runs swift2objc → swiftc -emit-objc-header → ffigen.
Config
tool/ffigen.dart for ObjC, tool/swiftgen.dart with SwiftGenerator(target:, inputs:, include:, output:, ffigen:) for Swift.
import 'package:ffigen/ffigen.dart';

Future<void> main() => FfiGenerator(
      input: Input(entryPoints: [Uri.file('src/wrapper.h')] /*, compilerOptions */),
      objectiveC: ObjectiveC(),
      output: Output(dart: DartOutput(path: Uri.file('lib/src/ios/av.dart'))),
      visitors: [Visitor(objCInterface: (n) => n.isIncluded = n.name.startsWith('AV'))],
    ).generate();
Commands
dart run tool/ffigen.dart, dart run tool/swiftgen.dart. Commit both .g.dart and .m: the latter must fall under the podspec's Classes/**.
Runtime
package:objective_c: ARC via NativeFinalizer, blocks .fromFunction / .listener / .blocking, protocols via $Builder.implementAsListener; package:ffi.
Build
podspec s.frameworks = 'AVFoundation' or SwiftPM linkerSettings: [.linkedFramework(...)]; ffiPlugin: true for ios and macos.
Pitfalls
  • Only @objc/NSObject-compatible Swift APIs are visible; structs and generics do not bridge.
  • Blocks from a foreign thread — only .listener/.blocking; UIKit and AppKit — main thread.
  • Without include filters ffigen pulls millions of lines from transitive frameworks; macros are not carried over.

Windows

stableffigen 22 · win32 6.4 · winmd 7.1 · native_toolchain_c
Input
C headers, your own or from the Windows SDK (Windows Kits\10\Include\…\um|shared). For Win32/COM — .winmd from NuGet Microsoft.Windows.SDK.Win32Metadata.
Generator
ffigen with compilerOptions: ['-I…']. Win32 — the pre-built package:win32, do not regenerate; for a custom slice — package:winmd as a metadata reader. C++ SDKs — an extern "C" shim built from hook/build.dart.

package:ffi, package:win32 (COM vtables, calloc/free).
Build

import 'package:hooks/hooks.dart';
import 'package:native_toolchain_c/native_toolchain_c.dart';

void main(List<String> args) => build(args, (input, output) async {
      await CBuilder.library(
        name: 'sdk_shim', assetName: 'sdk_shim.dart', sources: ['src/shim.c'],

Channels — pigeon C++ (cppHeaderOut, cppSourceOut).
Pitfalls
  • ffigen needs libclang on Windows too.
  • SAL annotations and __stdcall; MSVC redistributables when distributing.
  • pigeon C++ has forward-declaration bugs (flutter/flutter#128330).

Linux

C and D-Bus stable.gir immatureffigen 22 · dbus 0.7.15 · gir-binding-gen
Input
C headers with include paths from pkg-config --cflags gtk+-3.0; D-Bus introspection XML; .gir.
Generator
ffigen (this is how Canonical makes glib.dart and stdlibc.dart); dart-dbus generate-remote-object iface.xml -o lib/x.dart for a client, generate-object for a server; the community gir-binding-gen.

package:ffi, package:dbus.

Web

js_interop stableno generation from .d.tsdart:js_interop · package:web
Input
Browser APIs — WebIDL, already generated into package:web. JS libraries — .d.ts from npm or hand-written declarations.
Generator
For apps — hand-written extension types. Automation from .d.ts — only the unpublished js_interop_gen in dart-lang/web; js_facade_gen was archived in 2022.

What we do not do (YAGNI)

  • Our own runtime or dynamic dispatch.
  • Our own C++ parser — an extern "C" shim and a thin wrapper instead.
  • Preprocessor macro support.
  • GUI, mandatory AI dependencies, our own formatter and analyzer.

Plan and complexity

Every task in plan.md carries a complexity rating from C1 (mechanical, hours) to C5 (research-grade, no upstream to lean on) and a status. Work runs risk-first: IR, passes and facade synthesis first, then the .d.ts driver, then the ffigen adapter — the places where the design is most likely to be wrong. Estimates are for one experienced engineer; agents can parallelize phases 2–5. The toolchain is installed with mise from mise.toml.

11.5 weeks

Config, IR, first slice — the C driver C4config, IR, C driver, layout and CLI done

Typed config with JSON Schema and clear errors; IR model (done, with JSON snapshots); driver interface; C driver over ffigen through FfiGenerator and the visitor API — the public AST exposes names and inclusion but no types, so signatures are read from the generated Dart with the analyzer; emitter with hook/build.dart; commands init, doctor, generate, dump; golden tests on the fixture.

The config keeps one schema and uses it twice, which is the only way the two halves stay honest: the same document is exported for an editor's YAML language server and walked against the parsed file by the loader, so what gets underlined in an editor and what bindsmith refuses cannot drift apart. Shape is settled first — spelling, types, which keys exist — and nothing proceeds past a shape that did not hold; then meaning, which a schema states badly: that a platform names a driver or inherits from one that is configured directly, that headers: was not written under an Android entry, that a Maven coordinate parses, so a typo is caught while reading the file rather than when a download fails. Every problem is reported, not the first, and each one carries the line, the column and the offending line underlined. A key written under the wrong driver is an error rather than a key that quietly does nothing, which is the no-silent-drops rule wearing a config file. The bindsmith.yaml printed above loads verbatim as one of the tests, so this page and the loader cannot disagree.

Where a generated file goes turned out to deserve its own object rather than a line of path-joining at each call site. Three things have to agree about one file and none of them can see the others: the generator is handed an output path and an asset name before any content exists, the facade imports each binding by a path relative to itself, and the build hook declares the asset that the binding's own annotation names. Get the last pair out of step and nothing complains until the first call at runtime, which then has nothing to point at. So all three are derived from each other in one place, and the configuration gained the rule they depend on — generated Dart lives under lib/, because a file anywhere else has no package: URI and so no asset name. Iteration follows the platform list rather than the order the config file happens to be written in, so reformatting bindsmith.yaml cannot change a generated file.

The build hook is one file with one guard per platform, because a package may only have one and it runs once per target. Both flavours are emitted: one compiles the listed sources directly, the other runs an existing CMakeLists.txt, installs into the hook's own output directory and collects what appeared there, since CMake names the built file itself. Both are committed as fixtures and type-checked by the analyzer against the real upstream APIs — a snapshot test would only ever catch our own edits, never a renamed parameter three packages away.

The command line is where all of that finally meets, and it is deliberately one file that returns an exit code instead of ending the process. Everything it prints goes through sinks it was handed, and the directory it works in is an argument rather than the process's own, so the whole command line is exercised in memory against a throwaway project directory — thirteen cases in about a second, none of them starting a second Dart. The exit codes are the old sysexits ones, and the split is the reason to bother: a script needs to tell "your configuration is wrong" from "the generator broke", and a build that shells out to this deserves better than a bare 1. init writes the schema next to the config and points the file at it, so the editor completes the file it has just created; the test for that template does not compare it against saved text but loads it through the real loader, because what makes a starting point right is that it starts. Four of the six drivers are not wired in yet — each still needs something the configuration cannot say or resolve — and asking for one names the platform, names the driver and says how to leave it out, rather than generating nothing and reporting success. One test runs the whole thing twice and compares the bytes.

Done when: the fixture fixtures/c/geometry generates and compiles on Ubuntu and macOS.

22 weeks

Apple: Objective-C and Swift C4drivers and fixtures done

ObjC driver: completion handlers → Future, blocks from foreign threads → listener, the threading fixup. Swift driver through SwiftGenerator behind an adapter for the unstable API; Swift-only members recorded as dropped markers. podspec and SwiftPM emission.

Both fixtures are now built and called, not just generated and analyzed, because on Apple platforms the analyzer sees almost none of what can go wrong: a selector that does not exist fails at the call, a protocol written in Dart is only implemented once Objective-C dispatches to it, a block invoked from the wrong thread crashes, and an NSError** filled by the callee is invisible in the Dart signature. Swift adds three more, because the binding is three translations deep: the mangled class name only resolves if the module is really named what the wrapper thinks, a Swift struct only arrives as the wrapper class around it, and an async method reaches Dart as a completion handler that Swift invokes from its own executor thread — so it needs a listener block, and an ordinary one deadlocks. Building the Swift fixture is also the only check that the phase 7 bridge generator writes Swift a compiler accepts. The exercise paid for itself immediately: ffigen had been writing the glue's #import as a relative walk to the header it parsed, which for an absolute path meant a committed file carrying someone's home directory and building on no other machine. It now ships the header's own name, found through the include path a podspec sets.

Done when: the ObjC and Swift fixtures pass dart test on macOS; the podspec passes lint.

32 weeks

Android: jnigen, Maven, lockfile C4driver, Maven and the lockfile done

Maven resolver with transitive POMs and sha256 in the lockfile; JVM driver over JniGenerator; R8 keep rules, Gradle snippet; Kotlin fixture with overloads, an interface, suspend, Flow, default parameters; tests through Jni.spawn on a desktop JVM.

The Maven resolver is bindsmith's own, which was not the plan: jnigen resolves coordinates by writing a stub Gradle project and running gradlew, so there is no API to call and nothing that can be pinned. It reads POMs directly instead — parent inheritance, properties, dependencyManagement including BOMs imported with scope=import, optional and scope filtering, exclusions down the subtree, nearest definition wins. Parsing a POM is a pure function with its own tests, the way a pass is, and the fetch is injectable, so every resolution case runs against an in-memory repository and only one test reaches Maven Central. Two things only a real artifact could teach. A single repository is not enough: androidx.annotation:annotation-experimental is served by Google's Maven and the Kotlin standard library it needs only by Central, so repositories are a list searched in order. And a version range, LATEST or a snapshot is refused by name rather than resolved, because each makes one coordinate mean different bytes on a different day and there is nothing honest to write in a lockfile. The download cache mirrors the repository layout, so it is itself a Maven repository and the offline second run comes almost free.

The lockfile itself is short, and most of the design is about what it deliberately does not record. It does not name the repository that served the bytes: once the digest matches, which mirror answered does not change what you compiled against, and recording it would rewrite the file every time a team added one. It does not say which platform asked, because a coordinate names the same bytes whoever wanted it, and a dependency two platforms share should be downloaded and written once. Entries are sorted by coordinate, so reordering the configuration cannot produce a diff. A section whose resolver has not been written yet is refused by name rather than carried along, so a typo in the file cannot look like a working lock, and every problem is reported with its line and column the way a bad configuration is — this file is read by every offline build, and one it half-understands is worse than one it rejects. Re-resolving a coordinate whose bytes disagree with the lock is an error naming it and never a quiet rewrite: a released artifact does not change, so either the lock was edited or something is serving different bytes under that name. Offline is asked as a question rather than hoped for — the flag installs a fetch that throws, and since the download cache mirrors a repository’s own layout it is one, so a resolve it can answer never reaches for the network at all. Testing that end to end needed neither a network nor a test-only seam, because a repository may now be a file:// directory as well as an https:// one — which Gradle has always allowed and a vendored mirror on a shared drive actually wants — so the test publishes two artifacts into a temporary directory, resolves, deletes the repository, and resolves again offline. Plain http:// stays refused: an artifact fetched over it is one that whoever sits between you and the mirror chose, and it would then be pinned as if it were yours.

Done when: regeneration with the lockfile works offline; diff catches overload renumbering.

42 weeks

Web: the .d.ts driver C5driver and emitter done

A sidecar on the TypeScript Compiler API emits a JSON model of the declarations (done, with node tests); the driver turns it into IR and the emitter writes extension types with @JS, JSPromise → Future in the facade. A callback parameter takes a typed Dart function converted with .toJS, and an inline literal union such as 'formal' | 'casual' becomes a Dart enum named after where it was declared — both invented on the facade side, so the binding keeps saying exactly what the .d.ts said. Everything unsupported is a marker, never a silent drop. The generated code is compiled by both dart2js and dart2wasm in the test suite, which is not ceremony: it caught a bug the analyzer accepts, that a top-level external member needs its own @JS().

Done when: the nanoid, uuid and chart.js-subset fixtures compile to JS and Wasm.

62 weeks

Facade, passes, fixups, verify C5passes, facade and commands done

All passes as pure functions with unit tests (include, nullability and the fixups DSL are done); facade with conditional imports and runtime dispatch (done: throw/stub/omit policies, marshalling table, verify markers, goldens); the verify annotation blocks bindsmith verify until removed or acknowledged in the config; commands explain, diff, watch, generate --check.

The facade over C is where the design had to be sharpest, and it is split so neither half parses the other's output: a pure pass rewrites the dart:ffi types into the API the facade offers and leaves the dart:ffi spelling in the IR, and the emitter reads that spelling to decide how each value crosses. Strings go through an arena, an opaque handle keeps its pointer and gains a dispose, an enum crosses by constant name, and a struct is built with ffi.Struct.create — on the Dart heap, so it is garbage-collected and needs no dispose at all, which is the opposite of what the plan assumed. A struct passed by pointer is an arena copy read back field by field afterwards, because dart:ffi copies a struct into a pointer but has nothing that copies one out; without that, a C out-parameter would be silently lost. Every one of those was settled by calling a real compiled library, not by reading generated text.

The commands around generation turned out to be one idea rather than four. Every one of them is the same run with a different destination, so the pipeline was moved behind a single function that is told where the generators should write; a command that only reads points them at a directory it deletes afterwards. That is what makes the reproducibility check honest — it is the entire run again, into a throwaway directory, compared against what is committed, touching nothing in the tree it is checking, so continuous integration can run it on a clean checkout. It repaid the design immediately: because the throwaway directory has a different path every time, a check that passes also proves no generated file has recorded where it was generated, which is precisely the bug that had put a home directory into the Objective-C glue two phases earlier. The same change made printing the intermediate model read-only; until then it wrote a binding into the project as a side effect of showing you something. diff compares an earlier printout against the current sources symbol by symbol, and on shape rather than on the raw model, because review markers and doc comments move constantly while a changed signature is what actually breaks a caller. explain answers the question the markers exist for — why is this a pointer, why is this nullable, where did my method go — for one symbol, on every platform, with the reason attached. And watch keeps going while the configuration is broken, which is most of the time while someone is editing it, and takes its snapshot of the inputs before a run rather than after, or a header saved while generation is in flight is quietly absorbed and never rebuilt.

Done when: a six-platform fixture yields one library with an identical public API (checked with the analyzer).

82 weeks

Real examples, docs, release C4 / C3docs done

Five examples: AVFoundation, androidx.biometric, sqlite on desktop, chart.js on Web, a Swift-only package through the wrapper. Docs generated from the JSON Schema. Publishing to pub.dev, binaries on GitHub Releases (dart compile exe cross-compiles only to Linux, so build on each OS), Homebrew tap, pana ≥ 140.

The documentation is written, and the reference half of it is generated. A hand-written list of configuration keys drifts the moment someone adds one, and nothing fails when it does — so the reference page is walked out of the same schema an editor completes against and the loader rejects by, committed as a fixture, and a test fails when a new key has not reached it. Two more checks come cheaply from having the schema in hand: one walks it from the other side and fails on a key the page does not list, and one confirms every cross-reference on the page points at a heading that exists, computing the anchor the way the site will. The rest is prose that a schema cannot carry — what each driver needs on the host and what it will not do, a recipe per fixup with a note that acknowledging a marker is the one edit that can hide a real problem, and the order to upgrade in: record the API, bump, then diff. Publishing is one line of theme in the folder GitHub Pages already knows how to serve; nothing is installed and nothing is built.

Done when: all examples build in CI; packages are published; the docs site is live.

Project

Why bindsmith will beat what exists

  1. One declaration → six platforms and one facade. Today only flutter_rust_bridge does this, and only for Rust input.
  2. Web parity. .d.ts → dart:js_interop — no public tool since 2022; the pigeon Web issue has been open for four years.
  3. Pull model, declarative fixups and verify markers — a synthesis of CsWin32, objc2 and Sharpie; no Dart tool has any of it.
  4. Slim binding as a generated artifact, not advice in the docs.
  5. Dependencies and a lockfile — generation reproducible on CI without "build Android first".
  6. Resilience to upstream — pins, adapters, contract tests, diff after bumps.
  7. Docs and availability carried over into dartdoc and runtime checks.
  8. A size budget for generated code with a report of what can be excluded.
